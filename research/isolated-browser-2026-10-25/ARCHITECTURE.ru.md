# Изолированный браузер WebCodex: архитектура и сравнительное исследование

Дата: 2026-10-25.
Проект: W:\_python\webcdx.
Статус: проектное решение, без установки/изменения работающего браузера или авторизованных профилей.

## 1. Цель

Предоставить AI-агенту отдельный браузер с постоянными авторизациями, виртуальным графическим дисплеем, реальной программной мышью/клавиатурой и полноценным просмотром в отдельном окне Windows. Основные мышь, клавиатура и Chrome пользователя должны оставаться независимыми. Ускорить операции за счёт локального исполнения сценариев и адаптивного сочетания CDP/DOM и визуального управления.

**Ограничение:** невозможно гарантировать отсутствие обнаружения автоматизации или блокировки. Следовать правилам сайтов. Не разрабатывать подмену отпечатка/маскировку бота как обязательную часть решения.

## 2. Что обнаружено в текущем репозитории

- Go 1.25; зависимости chromedp 0.21.0 и cdproto 0.157.8.
- Gate, исходящий Windows/Linux agent, 10 браузерных MCP-операций, расширение MV3 и Native Messaging.
- Режим personal: использует уже открытые вкладки Chrome/Edge с авторизацией и локально разрешённым расширением. Не создаёт отдельную GUI-сессию.
- Режим persistent: собственный долгоживущий профиль WebCodex, авторизация сохраняется между запусками; требуется GUI/DISPLAY для видимого браузера.
- Уже реализованы alias/profile ID, discovery, reuse_only, binding_revision, сохранение исходного фокуса в большинстве действий, native input с read-back, light snapshot, чтение DOM-записей, проверка скачанных файлов и checkpoint-ориентированный capture store.
- В отчёте тестовой поставки 1.4.0 указаны Go/Node/Python/E2E тесты; не следует трактовать это как подтверждение обновления работающего агента Jinn, реальной personal-сессии или Linux GUI. Эти проверки явно отмечены как невыполненные.
- Существующий docker-compose.yml управляет Gate и его SQLite; не содержит контейнера браузера. Не добавлять браузер в контейнер Gate.
- Отдельный Linux agent нужно регистрировать в Gate как самостоятельный agent_id (например, jinn-browser), чтобы управлять его файловыми/браузерными ресурсами независимо от Windows agent.

Проверено на Jinn 2026-10-25: Windows NT 10.0 build 26200; доступны wsl.exe, docker.exe, Go, Python, git; WSL имеет Ubuntu-24.04, Debian и salad-enterprise-linux; Docker Desktop Linux daemon НЕ запущен (named pipe dockerDesktopLinuxEngine отсутствует). Ветка Git main, исходно чистая. Не проверено, есть ли Xvfb/Chrome/xpra внутри конкретного дистрибутива и доступен ли Hyper-V.

## 3. Архитектурное решение

### Этап A: короткий путь без виртуального компьютера

Выделенный постоянный Chrome-профиль в Windows (НЕ основная папка User Data), отдельный alias в расширении, CDP/Chromedp для большинства действий, focus_policy=preserve. Это позволяет агенту работать с вкладками без физических движений Windows-курсора. Для настоящего PyAutoGUI не подходит: desktop input в обычной пользовательской сессии Windows общий. Допускает окно наблюдения и хороший профиль-регрессионный тест.

### Этап B: основной рекомендуемый вариант — WSL2 Ubuntu 24.04

Windows (Jinn) -> WebCodex Gate -> отдельный Linux WebCodex agent -> Browser Worker.
Внутри WSL2:
- Изолированный виртуальный X11-display Xvfb (например, DISPLAY=:99), простая сессия оконного менеджера.
- Chrome / Chromium с user-data-dir на Linux ext4 в домашней директории сервиса, отдельный уникальный каталог для каждой логической identity. Каталог профиля нельзя одновременно открывать двумя Chrome-процессами.
- Локальный chromedp/CDP исполнитель, обычные действия по DOM/AX без GUI-фокуса и детерминированные retries на уровне команд.
- PyAutoGUI, запускаемый **внутри того же Linux DISPLAY**, для координатных кликов/ввода с использованием виртуальной мыши/клавиатуры. Запуск на Windows-хосте вместо Linux немедленно нарушит изоляцию.
- Xpra HTML5 для просмотра виртуального окна Chrome либо отдельный VNC-сервер с защищённым noVNC. Не открывать порт в интернет; bind на loopback + аутентификация и при удалённом доступе защищённый туннель.
- Отдельный Browser Worker (диспетчер задач) рядом с Chrome для исполнения многошаговых сценариев за один запрос. Не использовать полное LLM-рассуждение для каждого простого клика.
- Постоянная директория профиля и отдельный каталог downloads/manifest/checkpoints; файловые права 0700; резервное копирование после штатного закрытия браузера.

Пользователь открывает в основном Chrome вкладку localhost/Xpra и наблюдает за отдельным экраном. Агент не управляет основной мышью Windows. Когда пользователь вручную кликает по трансляции рабочего стола, его собственный ввод в это окно остаётся обычным взаимодействием с просмотрщиком; автоматически системный курсор агент не перехватывает.

### Этап C: контейнерный вариант

Когда Docker daemon доступен: отдельный контейнер Linux с Chrome, Xvfb/окнами, Python worker и persistent volume. Готовые основы:
1. linuxserver/webtop (текущий Selkies GUI stack; отдельная поддержка Chrome/запуска worker потребуется).
2. Steel Browser для browser API/session/UI; отдельно проверить реальные возможности сквозного PyAutoGUI на выделенном DISPLAY.
3. Самостоятельный минимальный Ubuntu/Chromium + Xvfb + Xpra + Python — больше конфигурации, но проще контролировать границы безопасности.

Контейнер — не равно полноценная VM по границам доверия. На Windows Docker Desktop обычно работает через Linux VM/WSL2. Рекомендуется не-root пользователь, seccomp, изоляция сети, ограниченные mounts, read-only RootFS где возможно, размер /dev/shm >= 1GiB, отключение лишних привилегий и недопустимость проброса docker.sock. Не использовать --no-sandbox как удобный способ исправить ошибки.

### Вариант D: отдельная Windows VM

Если нужны именно Windows GUI/Chrome расширения с нестандартной интеграцией, использовать Hyper-V/VMware с собственной полноценной пользовательской Windows-сессией и отдельным профилем Chrome. Ввод PyAutoGUI/Win32 внутри гостя не трогает основной хост. Дороже по RAM/CPU и сопровождению, чем WSL2. Windows-гостевая VM НЕ наследует автоматически сессионные cookies Chrome хоста.

## 4. Авторизованные профили

Предлагается один постоянный профиль агентского браузера и ручной первичный логин во все нужные сайты. После нормального выхода из Chrome и при следующем запуске сохраняются допустимые сайтом cookies и storage; авторизации могут истечь, быть отозваны или запрашивать повторную MFA.

Важные ограничения:
- Chrome/Playwright не допускают конкурентный запуск двух отдельных браузеров на одном user-data-dir.
- Chrome 136+ не разрешает remote-debugging-port/pipe на стандартном User Data; для CDP нужен неосновной user-data-dir. Chrome for Testing — официальный путь для задач тестовой автоматизации.
- Cookies Chrome Windows могут быть защищены платформенным ключом/привязкой к приложению. Простое копирование Windows User Data в Linux-контейнер не сохраняет входы и небезопасно.
- Google Sync не является способом перенести существующие веб-сессии/cookies.
- Локальный профиль агента — важный секрет. Запретить широкие mounts, публичный CDP/WebSocket, дампы cookie в журналы или загрузку профиля в облако без осознанного разрешения.

Для задач, когда критична ровно текущая сессия Windows без повторного логина, пользоваться существующим personal bridge WebCodex с точным profile_id/browser_alias; это отдельный режим **без физического PyAutoGUI**.

## 5. Стек фреймворков: что действительно стоит проверить

| Компонент | Функция | Решение |
| --- | --- | --- |
| chromedp/CDP | Точный быстрый DOM, input, download в Go | Сохранить существующий стек WebCodex |
| Playwright | Альтернативный/дополнительный deterministic action runner на Python/Node | Проверить как worker adapter, не переписывать Gate |
| Stagehand | act/observe/extract + восстановление селекторов с AI | Лучший AI кандидат; проверить локальный CDP/runtime и лицензию |
| Vercel agent-browser | Компактные AX snapshots, @refs, CLI/native производительность | Сравнить на одинаковых задачах |
| browser-use | Готовый AI агент на Python, CDP, persistent browser | Применять только как высокоуровневую стратегию |
| Steel Browser | Self-hosted API + session manager + UI | Кандидат на контейнерную инфраструктуру, не обязательный |
| Skyvern | Многоэтапный visual workflow/RPA | Тяжелее, вероятно избыточен для WebCodex; учесть AGPL |
| Xpra | Отдельный виртуальный GUI и HTML5-клиент | Предпочтительный просмотр одиночного приложения |
| LinuxServer Webtop | Готовый контейнер Linux desktop | Быстрый пилот Docker GUI |
| PyAutoGUI | Настоящие координатные нажатия в DISPLAY | Только fallback/специализированные действия |

Это shortlist, а не результаты локальных speed-тестов этих фреймворков. Маркетинговые заявления о миллисекундах, стоимости и устойчивости нельзя выдавать за независимые измерения.

## 6. Алгоритм максимальной эффективности

1. Зафиксировать целевой agent_id, browser profile_id, tab_id и проверенный URL/identity; исключить случайное открытие соседнего аккаунта.
2. Читать краткий scoped snapshot/records вместо целой страницы; повторно использовать revision и known IDs.
3. Детерминированно выполнять известные действия через chromedp/Playwright; не запрашивать LLM повторно для каждого элемента.
4. Для неопознанной UI-структуры использовать Stagehand/agent-browser или модель, затем сохранять валидированный workflow/action plan.
5. Если DOM/AX недоступен либо canvas/drag специфический, снимать скриншот **виртуального DISPLAY** и применять PyAutoGUI внутри WSL2; после действия проверять результат по DOM/изображению.
6. Выполнять последовательность локально внутри Browser Worker; в Gate возвращать краткий status + checkpointer + path готового файла. Новые мутации записывать в журнал до отправки, учитывать action IDs и неизвестный исход. Не выполнять невидимые повторы POST/submit.
7. Downloads сохранять как источник-оригинал, если сайт действительно отдаёт оригинал; сравнивать SHA-256, MIME, размеры, количество, вести manifest. Скриншоты сайта не подменяют исходный файл и его качество.
8. Для длинного виртуализированного списка — читать контейнер с устойчивыми record IDs и инкрементальную прокрутку, останавливаться по доказательству конца истории или фиксировать coverage неизвестным.
9. Использовать bounded concurrency по вкладкам и доменам; backoff при 429/503; стоп при challenge/MFA/сомнительном ответе.
10. Не использовать обход CAPTCHA, подмену браузерных отпечатков, прокси-ротацию для обхода санкций или автоматизированную работу вопреки правилам сайта.

Важное различие: быстрее за счёт меньшего числа RPC/LLM-циклов — не то же самое, что агрессивнее дёргать сервер. Сайту по-прежнему должны доставаться разумные запросы.

## 7. Протокольные изменения WebCodex

Первый MVP не требует ломать Gate: отдельный Linux агент с существующими browser_* tools, а одноразовые локальные операции PyAutoGUI можно проверять через разрешённые команды Linux агента. Чтобы сделать продукт полноценным:
- BrowserBackendAdapter для personal Windows / isolated Linux / Docker.
- Долгоживущий локальный Worker RPC, доступный только внутреннему Unix socket, а не публичному HTTP.
- browser_batch / browser_run_workflow с allowlisted шагами и атомарным audit/checkpoint, таймаутами и cancelled/unknown состояниями; не разрешать произвольный исполняемый код или URL из LLM без политики.
- computer_screenshot / computer_click / computer_type / computer_scroll / computer_hotkey, возвращающие подтверждение display/profile/session.
- browser_view_status и безопасное временное соединение наблюдателя, НЕ раздающее CDP.
- Policy: разрешённые домены/операции, отдельный emergency stop, максимальные bytes/time/steps/files и ручное согласование публикаций, платежей, MFA.
- Перед следующим выпуском выполнить уже закреплённое в AGENTS.md обязательное требование: вывод версии agent и Gate при старте, обмен настоящими версиями при соединении/reconnect, неизвестную версию явно обозначать.

Нельзя просто внедрить новый режим mode=isolated без проверки схем Gate/MCP, совместимости с версиями, client policy и тестов обновления.

## 8. План разработки и приёмки

### Фаза 0: оценка среды

Проверить, что WSL Ubuntu 24.04 может запускать Xvfb, Chromium, Xpra, Python и Linux Go agent; проверить ext4 место, права, сетевой доступ, DNS, звук/IME (если нужен). Не трогать существующие Chrome-профили, token и уже работающий Windows агент.

### Фаза 1: минимальная изоляция

Запустить Chrome на Xvfb, GUI просмотр локально в отдельном окне Chrome Windows, затем внутри guest PyAutoGUI открыть локальный test HTML, нажать кнопку и ввести Unicode. Параллельно пользователь двигает мышь/печатает в Windows. Успех: host focus/cursor не меняется, guest DOM показывает ожидаемый ввод, корректные DPI/координаты.

### Фаза 2: сохранение логина

Залогиниться **вручную** в тестовый сайт в отдельном профиле. Штатно остановить worker/browser, перезапустить, подтвердить сохранение permitted cookies/storage, отсутствие гонки второго процесса и сохранение файлов профиля. Специально протестировать истёкшую сессию без ложного статуса authenticated.

### Фаза 3: интеграция WebCodex

Отдельный agent_id, соответствующая регистрация Gate и разрешённые roots, логирование и отмена задач, version handshake, привязка tab/profile, ошибка при устаревших IDs, ручные MFA/CAPTCHA. Проверить безопасность Socket/CDP/VNC — только локально.

### Фаза 4: performance bake-off

На локальном тестовом сайте и разрешённых задачах сравнить chromedp, Playwright, Stagehand, agent-browser и browser-use: wall clock, медиана/p95 одного шага, число MCP/LLM вызовов, token consumption, успешность, correctness, RAM/CPU, recovery после SPA-перерисовки. Не путать локальный overhead и время загрузки реального сайта.

### Фаза 5: pilot реального workflow

Небольшая тестовая выборка разрешённых страниц: открыть запись, обнаружить вложение, скачать оригинал (если разрешено), проверить sha256, MIME, размеры, записать manifest, повторить без создания дубликатов, возобновить после аварии. Следить за соответствием правилам сайта; не автоматизировать запрещённый self-bot сбор пользовательских данных.

### Фаза 6: production hardening

Permissions, квоты, backup/restore, audit, update Chrome, recovery при crash, изоляция secrets, экспорт артефактов, аварийный Stop, тесты Docker/WSL перезапуска, минимальные права. Переход к Docker только после подтверждения стабильности базового worker.

## 9. Почему «работает как человек» не значит «не заблокируют»

Некоторые сервисы запрещают именно автоматизацию пользовательского аккаунта, независимо от наличия GUI и скорости кликов. Discord запрещает self-bots вне bot/OAuth API; LinkedIn запрещает сторонние расширения/ПО для автоматизации сайта. Никакой Xvfb, PyAutoGUI или «stealth» не дают гарантий от блокировки.

Корректная стратегия снижения риска — использовать разрешённые API, явные права, ограниченную частоту, одну стабильную сессию, понятные действия и ручные проверки спорных операций, а не скрывать автоматизацию.
