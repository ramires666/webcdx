# План прозрачности выполнения WebCodex

Дата: 2026-10-02.

Цель: видеть, какая команда получена из чата, что выполняется сейчас,
какой вывод появился и чем закончился процесс.

## Минимальный вариант — делаем сейчас

- [x] В терминале агента показывать command/argv, cwd и session ID перед запуском;
  после запуска — PID, timeout и пути stdout/stderr.
- [x] Дублировать новые stdout/stderr в терминал с session ID и названием потока.
  Экранировать управляющие символы, чтобы удалённый вывод не управлял терминалом.
- [x] Каждые 10 секунд показывать работающий процесс и прошедшее время, даже
  если новых строк нет. Печатать фактическое завершение, exit code, отмену,
  timeout и ошибки запуска независимо от последующих вызовов poll_command.
- [x] Различать успешный ответ инструмента и успешное завершение процесса:
  running не обозначать как завершение, ненулевой exit code показывать как ошибку.
- [x] Подробный вывод включён по умолчанию. WEBCODEX_VERBOSE=0 скрывает
  command/argv и содержимое stdout/stderr, сохраняя события и статусы.
  Значения env, stdin и токен агента не печатать. Команда и её вывод сами могут
  содержать секреты; автоматическое распознавание всех секретов не обещаем.
- [x] Усилить инструкции Gate и описания инструментов: перед выполнением
  сообщать команду и цель; использовать yield_time_ms около 1000–3000;
  пока процесс работает, опрашивать poll_command с возвращёнными offsets,
  публиковать существенные изменения примерно раз в 10–20 секунд и итог.
- [x] Сократить ожидание exec_command по умолчанию с 10 до 1 секунды,
  ограничить фактическое ожидание тремя секундами даже при запросе большего yield;
  чтобы долгий расчёт не удерживал один HTTP-вызов. Обрыв запроса не должен
  останавливать процесс. После Retry продолжать poll_command по прежней
  сессии, не запускать расчёт повторно. Проверить это runnable-тестом.
- [x] Дописать документацию и проверить запуск, вывод, завершение, ошибки,
  отключение подробностей, сохранение лимитов логов и совместимость v3/v4.
- [x] Запустить go test ./..., go vet ./..., собрать агент и Gate,
  закоммитить и запушить реализацию.

Ограничения: обновления текста чата зависят от вызовов модели и продолжения
её ответа, точный интервал не гарантируется. Агент сам не добавляет сообщения
в завершённый диалог. Буферизующий или молчащий процесс не сообщает свой
внутренний этап: показываем running и время, без выдуманного процента готовности.
Лимиты дисковых логов сохраняются; подробный терминал показывает приходящие
байты, в том числе после достижения лимита сохранения, с предупреждением.
Новые инструменты, UI и транспорт в минимальную версию не входят.

## Максимальный вариант — на вырост

1. MCP Apps UI внутри чата: карточка команды с cwd, PID, session ID, временем,
   статусом, раздельными stdout/stderr и кнопкой остановки. Автообновление
   через существующий poll_command с offsets, без пересказа каждой строки моделью.
   Проверить поддержку и ограничения конкретного клиента ChatGPT.
2. Страница мониторинга: активные и завершённые процессы по агентам,
   поиск, фильтры, просмотр и скачивание логов. Авторизация на каждый агент
   и команду; остановка использует существующие права cancel_command.
3. При необходимости общего потока событий — передача agent → Gate,
   подписки UI через SSE с восстановлением после разрыва, ограниченными
   очередями и обработкой медленного клиента. Текущий MCP SSE readiness
   не является реализацией прогресса. Сначала проверить, какие уведомления
   клиент действительно принимает и показывает.
4. Постоянный журнал событий: получение запроса, запуск, ошибки, завершение,
   отмена и timeout; связь request ID ↔ session ID, ротация и срок хранения.
   Секретные аргументы не сохранять без явно выбранного режима.
5. Прогресс этапов и проценты добавлять только для программ, которые сами
   сообщают такие данные. Метрики CPU/памяти — если появится реальная потребность.
6. Восстановление после Retry даже при потере ответа exec_command: список
   активных/недавних сессий и ключ идемпотентности запуска, чтобы повтор того же
   запроса не создавал второй процесс. Продумать права, сроки хранения ключей
   и неоднозначные повторы, не применять эвристику по совпадению текста команды.

## Длительные расчёты и обрывы чата

Наблюдение пользователя: долгий Python-расчёт приводит к разрыву в чате и Retry.
По проверенному коду: Gate ждёт отдельный вызов до WEBCODEX_CALL_TIMEOUT (60s
по умолчанию), exec_command до изменения ждёт 10s по умолчанию и до 30s явно.
Процесс имеет отдельный timeout_seconds: 1200s по умолчанию, максимум 86400s.
Контекст HTTP-запроса прекращает ожидание результата, но не убивает процесс.
NDJSON heartbeat Gate → agent каждые 5s поддерживает другое соединение;
локальный RUNNING тоже не продлевает жизнь запроса со стороны ChatGPT.

Минимальное решение: быстрый ответ с session ID и дальнейший polling, достаточный
timeout_seconds для самого расчёта; для Python при необходимости python -u
или PYTHONUNBUFFERED=1, чтобы вывод не задерживался в буфере. Не поднимать
таймауты вслепую и не держать один запрос до конца расчёта.

Без трассы конкретного сбоя нельзя определить, где именно сработал таймаут:
клиент ChatGPT, Gate или внешний reverse proxy. WebCodex не может гарантировать
бесконечный ответ модели или изменить таймаут клиента. Если session ID потерян
при обрыве первоначального ответа, автоматическое восстановление в минимальной
версии не гарантируется; ID виден в терминале агента. Максимальная версия
добавляет поиск сессий, защиту от повторного запуска и независимый UI.

Реализовывать последовательно по потребности: сначала карточка или страница,
затем общий поток событий. Не вводить отдельный брокер, новую БД и зависимости
для задач, которые покрывают существующие сессии и файловые логи.

## Подготовка репозитория

Минимальная реализация готова. Проверены go test -count=1 ./..., go vet ./...
и сборка Windows-бинарников в bin/webcodex-agent.exe и bin/webcodex-gate.exe.
Runnable-проверки подтверждают вывод до завершения, heartbeat, ненулевой
exit code, quiet mode, экранирование управляющих символов, лимит файловых
логов и продолжение процесса после отмены контекста запроса с последующим poll.
Проверены существующие тесты timeout, cancel, persistence и контрактов v3/v4.
Развёртывание на сервере и замена запущенного локального агента не выполнены.
Для применения обновить оба бинарника; новый агент выводит режим verbose
и каталог логов при запуске. Таймаут конкретного сбоя ChatGPT требует трассы.

Проверены и удалены 10 неотслеживаемых диагностических .txt файлов Ubuntu,
Plymouth и киоска из корня проекта; код на них не ссылается. Локальные бинарники,
скрипты запуска и command-логи сохранены. Подготовка и план публикуются
отдельным коммитом до изменения реализации.
