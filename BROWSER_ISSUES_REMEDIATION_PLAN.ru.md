# План устранения ошибок из LinkedIn browser audit

Дата анализа: 2026-10-24, Asia/Qyzylorda.

Исходный материал: `W:\_python\linkedin_profile_audit_20261024\LINKEDIN_BROWSER_AUTOMATION_ISSUES.md`, включая дополнения 18.1 и 18.2. Проверен код WebCodex на базе `b29af1e`. Версии бинарников Gate/agent и расширения, реально использовавшихся на Jinn, в отчёте отсутствуют: совпадение с текущими исходниками ещё нужно подтвердить.

Это результат анализа и план реализации. Исправления поведения инструментов в рамках этого этапа не выполнялись. До начала анализа в рабочем дереве уже было изменение `fill(contenteditable)` в `cmd/agent/browser_page.go`; оно не входит в этот документ и не считается проверенным исправлением описанных ошибок.

## 1. Основные выводы и приоритеты

Подтверждены четыре недостатка текущего кода:

1. `eval()` превращает любые JavaScript exceptions в `stale_element`, включая неверный option, неоднозначный locator, disabled и перекрытый элемент. Это напрямую объясняет ложный `stale_element` при `value="October"`.
2. Исходная причина ошибки теряется в журнале browser operation. Наружу остаются код и строка `browser operation ended: bop_…`, без полезного контекста.
3. `isBinary()` проверяет UTF-8 на срезе длиной 8192 байта. Если граница попадает внутрь символа, корректный текст отвергается. Этот случай воспроизведён на актуальном файле отчёта.
4. Snapshot не сообщает options селектов и контекст одинаково названных полей. Он ограничен по объёму, а `load` проверяет только `document.readyState`, поэтому готовность бизнес-интерфейса из этих данных не следует.

Есть также подтверждённые ограничения архитектуры: один текущий snapshot на вкладку и один выбранный personal bridge на manager; discovery нескольких браузеров требует изменения протокола, а не только добавления алиаса.

Сбой GitHub preview, ошибка LinkedIn reorder и разовая ошибка GitHub UI наблюдались в отчёте, но их первопричины не установлены. Устранение ошибок моста позволит лучше диагностировать и обходить эти сбои, но не гарантирует исправления стороннего сайта.

Приоритеты: **P0 — достоверные ошибки, защита от потери данных и повторной отправки; P1 — корректность чтения файлов, select/snapshot/wait и диагностика; P2 — расширенный discovery и удобство клиента.** Исправление UTF-8 небольшое и независимое, поэтому его целесообразно выпустить первым, несмотря на P1.

## 2. Разбор ошибок по исходникам

### 2.1. Ложный stale_element — подтверждено, P0

Код: `cmd/agent/browser_page.go`, функции `eval`, `locator`, `interact`, `elementPoint`.

Цепочка ошибки селекта:

```text
select(value="October")
  → DOM: нет option с value="October", throw Error('option')
  → eval: любое exceptionDetails становится stale_element
  → browser operation сохраняет только ErrorCode
  → operationResult: "browser operation ended: bop_…"
```

Аналогично маскируются `ambiguous`, `disabled`, `hidden`, `covered`, `not editable`, ошибки CSS-селектора и прочие исключения. В `locator()` ноль и несколько совпадений объединены в `ambiguous`; поиск role/name включает также скрытые узлы.

Исправление:

- Ввести контролируемый результат внутренних DOM-проверок с кодом и ограниченными структурированными деталями. Разбирать известные ошибки по этому контракту; неизвестное JS exception возвращать как `page_evaluation_failed`, без выгрузки сырого стека/страницы.
- Различать `stale_snapshot`, `element_detached`, `element_not_found`, `ambiguous_locator`, `invalid_option_value`, `element_disabled`, `element_hidden`, `element_obscured`, `frame_changed`, `navigation_pending`. Точные имена закрепить в контракте до реализации.
- Отдельно обрабатывать потерю execution context при навигации и реальную ошибку аргументов до обращения к странице.
- Проверять действие и тип элемента до изменения DOM. При неоднозначности возвращать число совпадений и безопасные признаки кандидатов, не выбирать первый.
- Сохранить публичную структуру `error.code`/`error.message`; расширение кодов и деталей проверить с клиентами. Если конкретный клиент жёстко зависит от старого кода, добавить переходное отображение на границе этого клиента.

Внешний `INVALID_ARGUMENT` из отчёта не объясняется полностью текущим кодом agent: он отдаёт MCP `isError` и внутренний код. Нужен один сквозной capture ответа agent → Gate → connector → клиент, чтобы определить, где появляется эта дополнительная классификация.

Приёмка: неверный select не возвращает stale; ноль, два совпадения, detached node и перекрытие имеют разные причины; результат одинаково понятен при прямом вызове и через Gate.

### 2.2. Потеря контекста ошибки и неоднозначный исход — подтверждено, P0

Код: `cmd/agent/browser.go`, `browserOperation`, `call`, `operationResult`; `cmd/agent/browser_operations.go`; `cmd/agent/native_executor.go`, `toolResult`; `cmd/agent/browser_bridge.go`, `callFrame`.

`browserOperation` сохраняет `ErrorCode`, но не исходное сообщение и детали. `operationResult()` заново создаёт ошибку с ID операции. При отказе расширения `callFrame()` также сводит причину к `personal browser rejected <method>`.

Уже реализованы уникальный `request_key`, проверка конфликта аргументов, журнал мутаций, TTL 24 часа и `outcome_unknown` для неопределённого исхода. Недавний коммит дополнительно защищает повторы при вытеснении истории. Переписывать эту подсистему с нуля не требуется.

Исправление:

- Хранить безопасные code/message/details и контекст: operation/session/tab/frame/snapshot, время, стадию выполнения и допустимое следующее действие. Не сохранять тексты форм и секретные аргументы в журнале ошибок.
- Делать эти данные доступными и из первоначального ответа, и из `browser_control(status)`, включая чтение журнала после рестарта. Старые journal entries без новых полей должны продолжать читаться.
- Разделить подтверждение доставки UI-действия и проверку результата сайта. `completed` у клика означает завершение dispatch, а не сохранение проекта или публикацию поста. Добавить признак уровня подтверждения без переопределения существующего статуса.
- При `running` продолжать status; при потере ответа повторять тот же ключ с теми же аргументами. Новому snapshot/locator соответствует новый набор аргументов: старый ключ нельзя использовать для него из-за `request_key_conflict`.
- При `outcome_unknown` сначала читать целевую страницу и проверять эффект. Новый ключ для Save/Post/Delete автоматически не создавать.

Универсальный bridge не может определить, какой клик необратим, только по подписи кнопки. По умолчанию не повторять клики/мутации после возможной отправки. Один повтор поиска допускается лишь при доказанном отказе ДО side effect; чтение можно повторять ограниченно.

Приёмка: ошибку можно связать с операцией без поиска ID в тексте; повтор status ничего не отправляет; потеря ответа после успешного submit не увеличивает счётчик отправок; старый журнал читается.

### 2.3. UTF-8 ошибочно считается binary — воспроизведено, P1, быстрый выпуск

Код: `cmd/agent/native_executor.go:482`, `isBinary`; вызовы в `cmd/agent/file_tools.go`: `readFile`, `editFile`, `searchFiles`, preview изменения файла.

Текущий алгоритм:

```go
sample := data
if len(sample) > 8192 { sample = sample[:8192] }
return bytes.IndexByte(sample, 0) >= 0 || !utf8.Valid(sample)
```

Проверка файла отчёта на дату анализа:

| Параметр | Результат |
| --- | --- |
| Размер актуальной версии | 36 419 байт |
| SHA-256 | `0f264a4436db3cb9ae4d8fdd18173132f643c1be34d1d54efa2419ed0ac13411` |
| UTF-8 всего файла | Корректен |
| NUL | 0 |
| UTF-8 первых 8192 байт | Некорректен: срез разрывает символ |

Это воспроизводит дефект классификатора на нынешнем файле. Первоначальная версия из отчёта имела 33 158 байт и не сохранена отдельно; байтовый результат именно той версии не проверялся.

Исправление: проверять NUL и `utf8.Valid(data)` по всему уже прочитанному ограниченному буферу. `readLimitedFile` возвращает полный файл в пределах лимита либо ошибку размера, поэтому искусственная выборка здесь не нужна. Не декодировать с молчаливой заменой повреждённых символов. Сохранить запрет NUL и существующие ограничения размера.

Тесты: ASCII; кириллица; 2-, 3-, 4-байтовые символы на каждой позиции около границы 8192; BOM; CRLF; файл >30 KB; NUL до/после 8192; повреждённый UTF-8 после 8192. Интеграционно проверить write → read с совпадением текста/хеша, edit и поиск по русскому тексту. Сейчас search может молча пропускать такие файлы, а edit — отказывать.

Приёмка: синтетический аналог отчёта корректно читается, редактируется и находится поиском; бинарные/повреждённые файлы не становятся текстовыми.

### 2.4. Select и одинаковые Month/Year — подтверждено, P1

Код: `cmd/agent/browser_page.go`, `browserDOM`, `snapshot`, `locator`, `interact`; `cmd/agent/browser_schemas.go`.

Сейчас snapshot содержит только текущее `value`; options не возвращаются. Select принимает исключительно точное value, отправляет `change`, не проверяет disabled option и не подтверждает сохранение выбранного состояния после обработчиков сайта. Контекста Start/End date в locator нет.

Исправление:

- Возвращать для native select `options: [{label, value, disabled, selected}]`, ограничение/признак усечения списка и контекст поля: доступный label, fieldset/legend или контейнер формы.
- Сохранить существующий `value`. Добавить явный способ выбора по label; для совместимого автоматического режима сначала точное value, затем единственный точный label. Коллизии и disabled option должны давать объяснимую ошибку.
- Добавить locator с ограничением контейнером; не использовать нечёткое совпадение и не выбирать первый Month. Проверять видимость/доступность с учётом выбранного действия.
- Применять события `input`/`change` в проверенном порядке и читать фактический результат после обработки. Повторная перерисовка не должна считаться успехом, если сайт сбросил значение.
- Проверить checkbox текущего проекта: скрытие end-date не должно менять start-date.

Приёмка: October/10 приводят к одному выбранному option; Start Month не затрагивает End Month; при скрытом End date выбор не попадает в скрытый контрол.

### 2.5. Snapshot, hydration и autocomplete — часть возможностей уже есть, P1

Код: `cmd/agent/browser_page.go`, `snapshot`, `wait`; состояние `snapshot`/`snapshotFrame` в `browserTab`.

В коде уже есть `truncated`, лимиты 10 000 DOM nodes, 300 interactive elements, 12 000 символов body text и дополнительное сокращение результата по бюджету ответа. Accessibility tree ограничивается 200 узлами отдельно; его усечение не всегда отражается общим флагом.

`browser_wait(element/text)` уже умеет ждать нужный элемент/текст. Поэтому базовое ожидание suggestions не требует нового инструмента. Однако `load` означает только `readyState === complete`; ошибки внутри ожидания, включая постоянные отказы, могут скрываться до общего `wait_timeout`.

У вкладки хранится один последний snapshot/frame, а в isolated world — один `__webcodex`. Новый snapshot, включая другой frame, делает старые element IDs непригодными по текущему контракту. Это не обязательно дефект, но причина должна быть явной. Внутри сессии уже есть mutex; он не защищает от перерисовки DOM самим сайтом между проверкой узла и dispatch мыши.

Исправление:

- Добавить observed metadata: время, frame/document generation, readyState, количество найденных/возвращённых узлов, отдельные причины усечения text/elements/AX/budget. Не обещать `complete=true` для всего LinkedIn: отсутствие DOM-мутаций не доказывает завершение lazy loading.
- Сначала scoped snapshot по контейнеру/секции. Пагинацию вводить только со snapshot-bound cursor и явной инвалидизацией после смены документа; простые offset по изменяющемуся DOM ненадёжны.
- Явно документировать срок жизни snapshot; не вводить MutationObserver, который делает snapshot stale при любой нерелевантной анимации.
- Для wait разделить временное отсутствие, неоднозначность и постоянные отказы доступа/frame. Не ждать 25 секунд при невозможности продолжать; возвращать конкретный код.
- На стороне сценария: direct section navigation только для реально доступных UI-маршрутов, затем bounded wait; autocomplete — ждать точный option либо видимое конечное состояние. `account-cap`, `no-match`, `loading` — вывод сценария по UI, а не универсальное знание bridge о LinkedIn.

Приёмка: задержанное появление About/options не даёт ложного «отсутствует»; усечение AX отражается; бесконечный loader заканчивается конечным timeout; чтение другой секции не приводит к неявному использованию старых IDs.

### 2.6. Project media preview, Back/Save и потеря формы — причина сайта неизвестна, P0 по сохранности данных

Источник: раздел 4 отчёта. Один URL сработал в Featured и не сработал внутри Project. Это разные UI-пути; успешный Featured не устанавливает причину отказа Project preview.

Bridge не управляет сервером preview и кодом модалки LinkedIn. Обещать «atomic save LinkedIn» или внедрять ручной link attachment, которого нет в UI сайта, нельзя. Возврат Back/Save может оказаться полностью связанным с маскировкой `covered`/`ambiguous`/stale ошибок; это нужно проверить после 2.1.

Решение по слоям:

1. **Сценарий:** держать подготовленные поля проекта в разрешённом локальном черновике вне журнала ошибок; сохранить основную запись до необязательных media, если сайт позволяет такой порядок. Проверить сохранённый текст чтением. Добавлять media отдельным редактированием.
2. **Bridge:** после ошибки preview получить свежий snapshot и diagnostics, определить реальную доступность Back/Cancel; не повторять старый element ID. Не делать reload/navigation формы до сохранения подготовленных данных и оценки возможной потери пользовательских изменений.
3. **Тестовый сайт:** воспроизвести вложенную модалку, rerender, overlay, preview 500/timeout. Проверить точность ошибок, возможность выйти и работу восстановления сценария. Это проверка WebCodex и алгоритма, не доказательство поведения реального LinkedIn.
4. **Реальный сайт:** один ограниченный повтор после закрытия media, только если состояние формы известно. Если превью недоступно, оставить основную запись и ссылку в описании/Featured как допустимый результат задачи, не повторять бесконечно.

Приёмка: сбой необязательного preview не ведёт к автоматическому сбросу введённого текста; основная запись проверена; при блокировке самого сайта есть понятный останов и данные для восстановления.

### 2.7. Diagnostics — уже реализованы, но слишком мало связующих данных, P1

Код: `browser-extension/background.js`, обработчик debugger events; `cmd/agent/browser_personal.go`, `recordBrowserEvent`; `cmd/agent/browser.go`, managed listeners; `cmd/agent/browser_page.go`, `browser_diagnostics`.

Есть bounded buffer на 100 событий, HTTP ≥400, console error/warning и очистка query/fragment. В personal event transport остаются в основном тип события и response status/url; для `Network.loadingFailed` теряются полезные request/error correlation fields, а содержимое console сознательно исключено. Отсутствие console text само по себе не баг: это действующая защита от утечки секретов.

Исправление: добавить request ID, допустимый enum причины сбоя, canceled, HTTP status, безопасный origin/очищенный путь, timestamp/duration и привязку к операции. Для расчёта duration хранить ограниченную карту request lifecycle с очисткой. Не добавлять полный сетевой trace по умолчанию.

Ошибки console по умолчанию — счётчик/категория. Любой дополнительный текст требует отдельной ограниченной и проверенной редактуры; предпочтительнее не передавать произвольные строки. URL path тоже может содержать персональные данные: недостаточно только удалить query. Для диагностики preview достаточно origin и нормализованного пути.

Приёмка: 500 и timeout можно отличить и связать с Add media; события из другой вкладки не смешиваются; тесты подтверждают отсутствие cookies, auth headers, request/response bodies, текстов форм и контрольных секретов.

### 2.8. Выбор Chrome/Edge и алиасы — архитектурное расширение, P2

Код: `cmd/agent/browser.go`, поле manager `bridge`; `cmd/agent/browser_bridge.go`, `serveBridge`; `cmd/agent/browser_personal.go`, `openPersonal`/`personalTabs`.

Текущий manager выбирает один bridge (`b.bridge = link`), не реестр нескольких профилей/браузеров. Каталог содержит разрешённые tab ID/URL, но не product/profile/window alias. Это подтверждённый пробел для однозначного выбора, хотя ошибочное переключение между Chrome/Edge в аудите не доказано.

Этапы расширения:

- Сначала получать подтверждённую bridge identity и локальный пользовательский profile alias при handshake; product/window сведения использовать только если они реально доступны разрешённым API. Не обещать соответствие PID/window без отдельного механизма.
- Заменить одиночный bridge на реестр соединений; определить поведение подключения/отключения и области sessions, request keys, pause и разрешённых tabs.
- Проверить цикл приёма IPC: сейчас `startBridge` вызывает `serveBridge` последовательно. Для одновременных соединений нужны независимое обслуживание, лимиты соединений и корректное завершение, а не только новая map.
- Добавить discovery только подключённых/разрешённых профилей. Это не глобальное перечисление вкладок ОС.
- Алиас привязать к подтверждённой identity профиля, а не к URL. URL LinkedIn может быть одинаковым у разных аккаунтов; ноль/несколько совпадений должны останавливать выбор.
- Добавить selector browser/profile/tab к контракту. После reconnect заново разрешать эфемерные session/tab IDs и подтверждать аккаунт по видимой странице.

Приёмка: одновременно подключены два профиля и Chrome/Edge; выбор однозначен; disconnect одного не меняет выбранный второй; локальная пауза и scope не обходятся алиасом. Общая discovery-функция ОС остаётся отдельной будущей задачей.

### 2.9. Screenshot — image block в серверном коде уже есть, P2

Код: `cmd/agent/browser.go`, `screenshot`; `cmd/agent/native_executor.go`, `toolResult`.

Уже возвращаются JPEG image content и metadata с размерами; `save=true` добавляет `artifact_path`. `truncated=true` при screenshot означает уменьшение изображения до бюджета, а не обязательно обрезку viewport или потерю image block. Screenshot image хранится в памяти операции; после рестарта journal сохраняет metadata, но не image payload.

План: проследить image block через agent/Gate/connector/оркестратор; проверить первичный ответ, running → status, потерю ответа и повтор после рестарта. Добавить ясные metadata о размере исходного/переданного изображения, масштабировании, byte size и доступности payload/artifact, не дублировать уже существующее `artifact_path` новым синонимом. Не объявлять изображение просмотренным по одной metadata.

Приёмка: клиент получает и отображает декодируемый JPEG; если доступна только metadata/артефакт, это явно указано; Gate не теряет image content.

### 2.10. Неверные вызовы, ограничения продукта и сбои сайтов — отдельная классификация

| Наблюдение из отчёта | Вывод | Действие |
| --- | --- | --- |
| `browser_tabs(action=create)`, URL в tabs | Ошибка клиента: контракт требует `new` и отдельную navigation | Примеры и preflight по реальной tools/list schema |
| Отсутствует action у navigate; `delta_y` у scroll | Ошибка клиента, строгая схема полезна | Не ослаблять валидацию; документировать поддерживаемый scroll |
| Выдуманный/старый snapshot ID | Ошибка вызова либо нормальная инвалидизация | Получать fresh ID; точный код причины |
| `running` трактуется как завершение | Ошибка workflow | Status до terminal, finite timeout |
| PowerShell потерял `$_` | Ошибка вложенной интерполяции | argv/скрипт без повторной интерпретации; короткие stderr |
| `cwd` вне roots | Ожидаемый отказ политики пути | Правильный рабочий каталог, не расширять roots ради обхода |
| 100/100 skills | Наблюдавшееся ограничение LinkedIn, не дефект bridge | Привязывать существующие skills; не удалять навыки автоматически |
| LinkedIn reorder: Something went wrong | Сайт сообщил ошибку; внутренний источник неизвестен | Diagnostics, ограниченный retry через опубликованный UI; сохранить текущий порядок |
| GitHub: UI service error | Единственный эпизод, недостаточно данных | Снять diagnostics при повторении; не объявлять репозиторий удалённым |

Изменения описаний tools и сценариев вне репозитория могут потребовать отдельного обновления клиентского плагина. Код WebCodex не может гарантировать поведение всех оркестраторов.

## 3. План реализации по этапам

Каждый этап заканчивается проверками, отдельным коммитом только своих изменений и немедленным `git push` в соответствующую ветку. Существующее незавершённое изменение contenteditable включать только в отдельный согласованный по объёму этап с собственной проверкой.

| Этап | Объём и результат | Зависимости | Проверка / пример заголовка коммита |
| --- | --- | --- | --- |
| 0. Анализ | Этот документ, воспроизводимая причина UTF-8, карта кода и границы выводов | Нет | Проверка ссылок/диффа и baseline; `Document verified browser failures and remediation stages (browser docs)` |
| 1. UTF-8 | Полный ограниченный буфер вместо разрезанного sample; read/edit/search/preview regression | Нет | Targeted file tests; `Validate complete UTF-8 buffers to avoid rejecting text files (file tools)` |
| 2. Ошибки и журнал | Типизированные DOM/transport ошибки, безопасный контекст, совместимое чтение журнала, сквозная MCP передача | Нет; выполнить до автоматического восстановления | Unit + mocked bridge + Gate contract; `Preserve browser failure causes across operation polling (browser protocol)` |
| 3. Select и locator | Options, выбор label/value, контекст Start/End, видимость и точная неоднозначность | 2 | Local managed и personal fixture; `Expose select options and scope repeated form labels (browser forms)` |
| 4. Snapshot/wait | Причины усечения, metadata, scoped read, корректные wait terminal states | 2; контракт согласовать с 3 | Delayed DOM/AX/iframe tests; `Report snapshot limits and wait for actionable UI state (browser snapshots)` |
| 5. Diagnostics | Correlation failed request → operation, длительность/причина, одинаковая редактировка personal/managed | 2 | Secret markers + bounded retention; `Correlate redacted browser failures with operations (browser diagnostics)` |
| 6. Восстановление форм | Черновик сценария, primary save отдельно от media, post-action verification, ограниченные retries | 2–5 | Preview 500/timeout + submit dedup + потеря ответа; `Recover form workflows without repeating submissions (browser workflows)` |
| 7. Discovery | Bridge registry, profile identity/aliases, явный выбор браузера/вкладки, reconnect | 2, 5; отдельный протокольный дизайн | Два одновременных bridge + pause/revoke/isolation; `Resolve personal browser aliases across connected profiles (browser discovery)` |
| 8. Screenshot/client docs | Сквозная image delivery, ясная metadata, проверенные примеры инструментов и ограничения workflow | 2; можно раньше 7 | Agent → Gate → реальный клиент; `Verify image delivery and document browser recovery (MCP integration)` |
| 9. Приёмка и выпуск | Регрессионный прогон, проверка версий на Jinn, обновление руководства, ограниченная ручная проверка сайтов | 1–8, либо явно сокращённый релиз без 7 | Версии и результаты записаны; `Document browser reliability acceptance and rollout (release docs)` |

Рекомендуемая первая поставка: этапы 1–6 и клиентская проверка image. Discovery выпускать отдельно: это самый широкий протокольный этап, он не должен задерживать исправления доказанных ошибок. Ключевые зависимости: 2 → 3/4/5 → 6; 7 не блокирует базовый recovery при явном выборе tab.

Общее условие всех API-этапов: одновременно менять реализацию, `browser_schemas.go`, серверную валидацию, примеры и проверки Gate. Output objects используют `additionalProperties=false`: новые options/context/error metadata нельзя просто дописать в JSON без изменения объявленного контракта. Проверить success/error/running ответы, группы агентов с разными версиями схем и обновление tool metadata клиентом. Совместимые поля вводить как optional; действительно несовместимое изменение требует отдельного решения о версии контракта до реализации.

Предварительная оценка одного разработчика: 6–10 рабочих дней на этапы 1–6 и screenshot/docs, ещё 3–5 на discovery, 1–2 на приёмку. Это оценка по прочитанному коду, без подтверждённых версий Jinn и без обещания срока устранения внутренних сбоев LinkedIn/GitHub. После этапов 1–2 оценку уточнить.

## 4. Матрица проверок и критерии выпуска

1. **Файлы:** символы UTF-8 вокруг 8192; NUL/invalid UTF-8; read/edit/search/preview; неизменность исходных данных и SHA-256 при чтении.
2. **Ошибки:** old snapshot, detached element, отсутствующий/неоднозначный locator, disabled/covered, неверный select и потеря frame возвращают различимые коды через весь MCP-путь.
3. **Формы:** две пары Month/Year; option label October/value 10; rerender на change; hidden end date; асинхронные suggestions; account-cap без удаления skills.
4. **Снимки:** delayed hydration, >12k text, >300 elements, >200 AX nodes, response budget, snapshot другого frame, full document navigation. Во всех случаях metadata не создаёт ложного впечатления полноты.
5. **Повторы:** успешный submit с потерянным ответом; status; тот же request key; конфликт аргументов; cache eviction; restart; TTL; `outcome_unknown`. Счётчик submit остаётся 1 там, где первая отправка произошла.
6. **Восстановление:** preview 500/timeout/вечный loader; после ошибки fresh locator; закрытие модалки; сохранность подготовленных данных; ни reload, ни повторный submit не происходят автоматически при неизвестном исходе.
7. **Discovery:** два browser connections, два одинаковых URL, ноль совпадений, reconnect, закрытая вкладка, локальная пауза, отзыв доступа. Никакого молчаливого fallback в другой профиль.
8. **Диагностика/image:** секретные контрольные строки отсутствуют, лимиты памяти соблюдены; JPEG проходит прямой ответ и running/status; metadata после рестарта не выдаётся за доступный image payload.

Команды при реализации: targeted `go test` затронутых пакетов, затем `go test ./...`, `go vet ./...`, `node --test browser-extension/background.test.cjs`; `go test -race` для изменений concurrent registry/journal на поддерживаемом окружении. Перед коммитом — `git diff --check` и проверка состава staged files.

Managed browser tests включаются отдельно через `WEBCODEX_BROWSER_TEST=1`; обычный прогон их пропускает. Для personal нужен отдельный локальный тестовый сайт и тестовое подключение расширения, а не публикация в рабочем LinkedIn. Проверить Windows Chrome/Edge; Linux — на доступном Linux-окружении, с явной записью непроверенных платформ.

Ручная приёмка в авторизованном LinkedIn — после локальных регрессий и только в объёме конкретного поручения на изменения профиля. Исходный аудит не является разрешением повторно публиковать пост, менять порядок Featured или удалять навыки. Read-only проверка страницы/версий и подготовка тестового сайта не требуют таких внешних изменений.

Критерии первой поставки: нет ложного stale для invalid option; корректный UTF-8 читается; ясны усечение и ожидание; ошибка preview не вызывает автоматическую потерю подготовленных полей; неизвестный исход не порождает второй submit; причины доступны через status и MCP; существующие scope/pause/revoke и журналы продолжают работать.
