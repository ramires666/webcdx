# План разработки: управление полноценным браузером из чата

Дата: 2026-10-02. Обновление: 2026-10-12. Реализация начата.

Реализованы clean/persistent/personal с десятью инструментами v5,
MCP image, iframe (включая отдельный процесс)/open shadow DOM,
upload/download, popup, паузой, ограниченными журналами и устойчивым Retry.
Windows Chrome проверен в headless и видимом режиме; Edge проверен на
локальном E2E-сайте. Проверены весь путь MCP → Gate → agent → Chrome,
единственный submit при Retry, сохранение постоянной авторизации,
personal IPC с уже авторизованной тестовой вкладкой и отзыв доступа.
Тесты расширения проверяют scope, паузу, iframe и отсутствие секретов.
Регистрация/установка в обычном профиле, Linux GUI, живой поиск Google
и отображение MCP image в целевом клиенте остаются ручной приёмкой.
Это ограничения выполненной проверки, а не отмеченные выполненными этапы.
Инструкция: [BROWSER_GUIDE.ru.md](BROWSER_GUIDE.ru.md).

## Цель и критерий готовности

Добавить в WebCodex возможность из чата управлять настоящим видимым браузером
на компьютере пользователя: искать в Google, открывать сайты, переходить по
ссылкам, заполнять формы, тестировать интерфейсы и работать после авторизации.
Опционально использовать уже существующую сессию пользователя с его cookies.
Трафик сайтов должен идти с компьютера пользователя, через его браузер и сеть.

Работа считается завершённой, когда доступны все три режима ниже, базовые
браузерные операции и диагностика, а сценарии приёмки проходят через MCP.
Только чистый автоматизированный профиль не закрывает требование о моих cookies.

## 1. Что уже есть и что переиспользовать

Сейчас проект — Go MCP Gate и локальный агент, а не приложение со своим чатом.
Клиент чата вызывает инструменты; агент выполняет действия на компьютере.

| Существующая часть | Как использовать |
| --- | --- |
| `cmd/gate/mcp.go`, `server.go`, `oauth.go` | MCP, OAuth и маршрутизация вызовов к нужному агенту. |
| `cmd/gate/tool_policy.go`, `admin.go` | Разрешения браузерных инструментов на уровне агента. |
| `cmd/agent/native_executor.go`, `tool_schemas.go` | Диспетчеризация и явные JSON-схемы новых инструментов. |
| `cmd/agent/gate_stream.go`, `internal/protocol/protocol.go` | Существующий исходящий NDJSON и ответы, без нового публичного порта на компьютере. |
| `cmd/agent/action_log.go` | События браузерных операций без секретных аргументов. |
| `cmd/agent/file_tools.go` | Проверки разрешённых путей для загрузок и выгрузок файлов. |

В `go.mod` браузерной библиотеки сейчас нет. Для управляемого Chromium предлагается
одна зависимость — `chromedp`, Go-клиент CDP. Это проектное решение: подтвердить
на прототипе до реализации полного набора инструментов. Библиотека управляет
браузером по CDP, без обязательного отдельного Node-сервиса.
[Документация chromedp](https://github.com/chromedp/chromedp).

## 2. Режимы браузера

| Режим | Поведение | Авторизация |
| --- | --- | --- |
| `clean` | Видимый Chrome/Chromium с временным отдельным профилем. | Без личной сессии; состояние удаляется при закрытии. |
| `persistent` | Видимый Chrome/Chromium с отдельным постоянным профилем WebCodex. | Пользователь один раз входит вручную; браузер сохраняет сессию между запусками. |
| `personal` | Расширение подключает выбранные вкладки обычного браузера пользователя. | Используются существующие cookies и состояние сайта прямо в этом профиле. |

Chrome — первая поддерживаемая платформа; Edge на Windows проверяется отдельно.
Локальный агент поддерживает Windows/Linux: видимому браузеру нужна интерактивная
пользовательская сессия. Для Linux проверить совместимость service-unit и GUI;
Windows-служба без рабочего стола не должна обещать видимое окно. Firefox/Safari
потребуют отдельного адаптера и не входят в первую реализацию.

«Полноценный браузер» означает обычное окно и настоящий браузерный движок,
доступ к интернету и локальным тестовым сайтам. Встроенную защитную песочницу
Chrome сохраняем: требование выйти из песочницы инструментов чата не требует
запуска Chrome с `--no-sandbox`.

### Почему личный профиль подключаем через расширение

Начиная с Chrome 136, remote debugging основного каталога профиля ограничен:
для этих флагов требуется нестандартный `--user-data-dir`. Поэтому нельзя
планировать подключение к обычному Chrome только через `--remote-debugging-port`.
[Официальное изменение Chrome](https://developer.chrome.com/blog/remote-debugging-port).

Для `personal` разработать расширение Manifest V3 с `chrome.debugger`, выбирающее
вкладки для управления. API предоставляет CDP-доступ к вкладкам, но имеет ограничения
по доступным доменам протокола; совместимость операций проверить прототипом.
[Документация chrome.debugger](https://developer.chrome.com/docs/extensions/reference/api/debugger).

Cookies не требуется копировать: браузер сам применяет их при запросах.
Сохранённая авторизация может также зависеть от localStorage, IndexedDB и других
данных, поэтому перенос только cookies не равнозначен работе в исходной сессии.
Не читать базу cookies основного профиля и не расшифровывать её самостоятельно.
Отдельный импорт cookies не нужен для первоначальной реализации этих режимов.

## 3. Архитектура

```text
Чат → MCP / OAuth → существующий Gate → существующий локальный agent
                                         ├─ chromedp / CDP → видимый браузер
                                         │                  clean / persistent
                                         └─ локальный IPC → Native Messaging host
                                                            ↕
                                                      расширение → personal
```

- Браузер запускается и управляется на компьютере пользователя; Gate не запускает
  удалённый браузер и не хранит профиль.
- Сначала реализовать прямой CDP-путь без универсального фреймворка драйверов.
  При добавлении расширения выделить только реально общие операции.
- Для расширения использовать Native Messaging и небольшой режим host в том же
  бинарнике агента. Chrome запускает host отдельным процессом: он связывается
  с уже работающим агентом через локальный IPC, а не создаёт второй Gate-agent.
  На Windows — named pipe с ACL пользователя, на Linux — Unix socket с правами
  владельца; аутентификация соединения и проверка отправителя обязательны.
- Регистрация host ограничивает `allowed_origins` ID установленного расширения;
  установка и удаление регистрации входят в поставку. Framing Native Messaging
  отличается от NDJSON, а лимиты сообщений требуют ограничения размера снимков.
  [Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging).
- CDP-порт, если нужен библиотеке, доступен только через loopback. Не публиковать
  его на Gate и не принимать произвольный удалённый debugging URL из чата.
- Каждая сессия получает непрозрачный `browser_session_id`; вкладки имеют `tab_id`.
  Сессии принадлежат конкретному агенту. Другой агент не может обращаться к ним.
- Браузер живёт независимо от отдельного HTTP-вызова. Операции получают собственный
  deadline; истечение ожидания не должно автоматически закрывать личный браузер.

## 4. Предлагаемый контракт MCP

Добавить `/mcp/v5`, сохранив неизменными списки и поведение v3/v4. v5 включает
существующие v4-инструменты и браузерные операции. При отключённой локальной
браузерной функции инструменты не публикуются и прямые вызовы отклоняются.

| Инструмент | Назначение |
| --- | --- |
| `browser_open` | Создать clean/persistent-сессию либо подключиться к локально разрешённой personal-сессии. |
| `browser_tabs` | Список доступных вкладок, создание, выбор и закрытие вкладки через явный `action`. |
| `browser_navigate` | URL, назад, вперёд, перезагрузка; финальный URL и статус навигации. |
| `browser_snapshot` | Текст и дерево доступности, ссылки, поля, элементы с идентификаторами. |
| `browser_screenshot` | Снимок viewport или всей страницы как MCP image и при необходимости локальный артефакт. |
| `browser_interact` | Click, fill, select, hover, press, scroll, drag; явные варианты схемы аргументов. |
| `browser_wait` | Ограниченное ожидание элемента, URL, текста или завершения загрузки. |
| `browser_files` | Загрузка разрешённого локального файла и получение статуса скачивания. |
| `browser_diagnostics` | Ограниченные console errors и сведения о неуспешных сетевых запросах. |
| `browser_control` | Статус, пауза, продолжение, отмена операции, отключение сессии. |

Общие требования к контракту:

- Явные схемы с `additionalProperties: false`; допустимые действия — enum/oneOf.
  Не делать инструмент выполнения произвольных shell-команд или сырого CDP.
- Ответ: session/tab ID, статус, фактический URL, данные, `truncated`, код ошибки.
  Статусы отдельно от статусов command-сессий: `ready`, `running`, `waiting_user`,
  `paused`, `completed`, `failed`, `cancelled`, `disconnected`.
- Снимок возвращает `snapshot_id`; идентификатор элемента действует в пределах
  соответствующего снимка и frame. После навигации устаревший ID вызывает ошибку,
  а не клик по другому элементу. Дополнительно поддержать точные role/name и CSS
  локаторы; неоднозначный выбор не разрешать первым совпадением молча.
- Поддержать SPA, iframe, shadow DOM, popup, новые вкладки, alert/confirm/prompt,
  OAuth-редиректы. Координатный клик — явный запасной вариант с размерами viewport.
- Скриншоты требуют доработки `toolResult`: сейчас ответы содержат только text
  и structuredContent. Проверить image content в реальном MCP-клиенте.
- Учесть текущий предел `/agent/result` 2 MiB и default response 256 KiB:
  изображения уменьшать/сжимать в пределах полного JSON/base64-конверта;
  большие текстовые снимки ограничивать, диагностические события выдавать порциями.
- Вызов должен отвечать до timeout Gate, сейчас 60 секунд по умолчанию.
  Долгая операция возвращает `operation_id`, затем статус читается отдельно.
- Мутации получают `request_key`: повтор после потери ответа возвращает известный
  результат. При неизвестном исходе — `outcome_unknown`, без повторного submit.

## 5. Управление доступом и личной сессией

- Браузерная функция включается локально; личный режим отдельно разрешается в
  расширении. Разрешения Gate дополнительно ограничивают конкретные инструменты.
  MCP annotations — подсказки, не механизм авторизации.
- В расширении: выбор подключаемых вкладок, видимый индикатор управления, кнопки
  «Пауза» и «Отключить». Область доступа проверяется расширением/агентом при каждом
  действии, после редиректа и открытия popup; неизвестная вкладка не подключается
  автоматически. Пользователь может разрешить новые вкладки для текущей задачи.
- Режим поиска по публичному интернету не требует разрешения каждого результата.
  Использование личной авторизации — отдельная настройка. Google открывается как
  обычный сайт, запрос формируется с URL-кодированием, аккаунт определяется выбранным
  профилем; chat не должен утверждать, что поиск выполнен с аккаунтом без проверки.
- Обычные чтение, поиск и тестовая навигация выполняются в выбранной области
  доступа без повторных вопросов. Для тестовых сайтов можно заранее разрешить
  изменение данных. Покупки, отправка сообщений, удаление и другие внешние изменения
  выполняются при наличии конкретной авторизации пользователя.
- URL разрешают HTTP/HTTPS; localhost и intranet нужны для тестов и управляются
  настройкой области доступа. `file:`, `chrome:`, `javascript:` и доступ к чужим
  расширениям через инструменты отклоняются; редиректы тоже проверяются.
- Cookies, Authorization, пароли и полный storage не возвращаются в чат и логи.
  Диагностика по умолчанию исключает headers/body, query-секреты и поля паролей.
  Содержимое авторизованных страниц и скриншоты, которые запрошены для задачи,
  проходят через Gate к клиенту; это отдельно объяснить при включении personal.
- Текст сайта — данные, не инструкции агента. Проверки доступа не могут зависеть
  только от поведения модели: ограничения исполняются в коде агента/расширения.
- Upload/download проходят существующую проверку разрешённых путей, включая
  symlink/reparse и запрет перезаписи без предусловия. Скачанное не запускать.
- Профили остаются локально с правами владельца; не попадать в репозиторий,
  SQLite Gate, диагностические архивы и стандартные логи. Хранение артефактов
  ограничить сроком и размером; clean-профиль очищается после завершения.
- Отключение personal отсоединяет управление, сохраняя браузер пользователя.
  Закрывать только созданные агентом окна/вкладки согласно выбранной настройке.

### Этап 1 — браузер без личных cookies

- [ ] Добавить управление жизненным циклом браузера в `cmd/agent/browser.go`,

- [ ] Предлагаемые настройки: `WEBCODEX_BROWSER_ENABLED=0`, путь браузера,

  профильный путь, executable или флаги запуска.
- [ ] Реализовать clean/persistent, вкладки, навигацию, snapshot, screenshot,
  основные взаимодействия, ожидание и остановку.
- [ ] Добавить v5: маршруты и OAuth metadata в Gate, контрактный marker,

  v5 должен наследовать v4-файлы и команды, а не случайно включать старый контракт.
- [ ] Обновить инструкции MCP и action log; браузерные статусы не должны
  отображаться как статусы процессов с exit code.

Выход: из чата можно искать и тестировать сайт в видимом окне, повторный вход
в постоянном профиле не требуется, пока сервер сайта сохраняет сессию.

### Этап 2 — существующая личная сессия

- [ ] Добавить `browser-extension/`: Manifest V3, подключение выбранной вкладки,
  индикатор, паузу и отзыв доступа; минимальные необходимые permissions.
- [ ] Добавить Native Messaging host и установку/удаление его регистрации
  для Windows/Linux; реализовать IPC с работающим агентом.
- [ ] Подключить personal к тому же MCP-контракту; общие проверки выполнить
  для обоих путей, не полагаться на прямую передачу произвольных CDP-команд.
- [ ] Обработать восстановление соединения, смену вкладки, logout и отзыв
  разрешения. После переподключения не расширять ранее разрешённую область.
- [ ] Пользователь вручную проходит пароль, MFA, CAPTCHA и consent в браузере;
  агент возвращает `waiting_user`, после проверки состояния продолжает задачу.

Выход: чат работает в обычной авторизованной вкладке пользователя без копирования
cookies. Этот этап обязателен для полного выполнения исходного требования.

### Этап 3 — завершить тестовые возможности

- [ ] Завершить формы, iframe/shadow DOM, popup/dialog, drag, upload/download,

- [ ] Последовательно исполнять изменения одной вкладки; чтения не возвращают

- [ ] Реализовать operation status, отмену, дедупликацию request_key,

  проверить поведение при достижении лимитов без потери личного профиля.

Выход: все заявленные операции работают в поддерживаемых режимах; отличия
возможностей расширения и прямого CDP явно отражены в ответах и документации.

### Этап 4 — приёмка, документация и выпуск

- [ ] Автоматические Go-проверки: схемы v5, неизменность v3/v4, policy deny,

  параллельные операции, отмена и повтор запроса после потери ответа.
- [ ] Локальный E2E-сайт с login, cookie-сессией, формой-счётчиком submit,

- [ ] Проверить IPC: чужой пользователь/расширение не подключается, отзыв
  разрешения останавливает новые команды, cookies/пароли не появляются в логах.
- [ ] Ручная приёмка personal на тестовом аккаунте и реального поиска Google;
  живые личные аккаунты и Google не использовать в автоматических тестах.
- [ ] Запустить `go test -count=1 ./...`, `go vet ./...`, собрать Gate/agent,
  проверить установку расширения на Windows и Linux.
- [ ] Обновить README, USER_GUIDE, `.env.example` и инструкции запуска в GUI-сессии:
  режимы, права, вход/MFA, очистка профилей, подключение и аварийное отключение.
- [ ] Выпуск: сначала Gate с v5, затем агент и расширение, затем подключение
  клиента к v5. Откат: отключить браузер, вернуть v4; личные профили не удалять.

## 7. Сценарии приёмки пользователем

1. «Погугли запрос и сравни три результата»: видимое окно, действительные
   переходы и ссылки, запрос выходит через сеть компьютера пользователя.
2. «Проверь сайт после входа»: пользователь логинится в persistent, чат видит
   закрытый раздел; после перезапуска профиль сохраняется.
3. «Используй мои текущие cookies»: пользователь подключает авторизованную
   personal-вкладку; чат работает без нового входа и экспорта cookies.
4. «Проверь форму»: заполнение, проверка ошибок, отправка в разрешённой
   тестовой среде, screenshot и console/network диагностика.
5. «Загрузи файл и скачай отчёт»: пути проверяются, чужой файл недоступен,
   скачивание не перезаписывает данные незаметно.
6. CAPTCHA/MFA останавливает автоматические действия до ручного завершения;
   ожидание не держит один HTTP-запрос до разрыва чата.
7. «Пауза/отключить»: новые действия сразу блокируются, исходный личный
   браузер и аккаунт продолжают работать.
8. Закрытие вкладки, обрыв Gate, рестарт агента и Retry дают понятный статус;
   повтор внешнего действия не происходит автоматически.

## 8. Границы первой реализации

В первую полную поставку входят все три режима, включая personal. Не добавляем
облачную ферму браузеров, Selenium Grid, отдельный Node-сервис, собственную
поисковую систему или экспорт всех cookies: текущий агент, CDP и расширение
покрывают задачу. Дополнительные движки и видеотрансляция — отдельные задачи
при подтверждённой потребности.

Полноценный браузер не гарантирует обход антибот-проверок, CAPTCHA или правил
сайта. Истечение сессии и требование повторного входа определяет сайт. Работа
«от моего имени» означает выбранный аккаунт и его браузерную сессию, а не
безусловный доступ ко всем аккаунтам, вкладкам и внешним действиям.
