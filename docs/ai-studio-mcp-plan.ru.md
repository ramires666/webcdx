# WebCodex MCP в веб-чате Google AI Studio без AI-ключей

Дата исследования: 2026-11-11. Статус: исходный план разработки.

Реализация alpha находится в отдельной папке
[ai-studio-extension](../ai-studio-extension/README.ru.md). Живая приёмка в AI Studio
пока не выполнена. Описание исходного репозитория ниже фиксирует состояние до
реализации; требования к полноценному выпуску остаются критериями приёмки.

## 1. Решение

Сделать отдельное расширение Chrome **WebCodex AI Studio Bridge**. Модель работает
в существующем веб-чате AI Studio под аккаунтом пользователя. Расширение получает
из законченного ответа модели структурированный запрос инструмента, выполняет
его через наш Gate и отправляет результат обратно в этот же чат. Модель продолжает
работу средствами сайта.

**Обязательное условие: никаких Gemini/OpenAI API keys и самостоятельных запросов
к API модели.** Расширение не запускает вторую модель, не подменяет запросы Google
и не использует cookies Google для стороннего клиента. Доступность модели,
квоты и ограничения веб-чата остаются ограничениями самого AI Studio.

Авторизация к WebCodex Gate всё равно нужна: это доступ к компьютеру пользователя,
а не ключ AI-провайдера. Токен Gate хранится в доверенной части расширения и не
попадает в сообщения AI Studio.

```text
Пользователь ↔ веб-чат AI Studio ↔ Gemini на стороне Google
                        ↕ запрос инструмента / результат в диалоге
              content script отдельного расширения
                        ↕ сообщения Chrome
              service worker + боковая панель
                        ↕ HTTPS, авторизация WebCodex
                    WebCodex Gate
                        ↕ существующее исходящее соединение агента
                    WebCodex agent
                        ↕
                  файлы, команды, MCP-инструменты
```

Это адаптер к существующему WebCodex, а не новая реализация MCP-сервера.

## 2. Что проверено и что пока неизвестно

### Документация Google

В обычном Chat prompts Google описывает function calling в настройках.
Это само по себе не подтверждает возможность выполнить произвольный MCP-вызов
и автоматически вернуть его результат через интерфейс конкретного аккаунта.
Источник: [AI Studio quickstart](https://ai.google.dev/gemini-api/docs/ai-studio-quickstart).

Отдельно Google уже описывает внешние MCP-серверы в режиме **Playground → Agents**.
Поэтому утверждение «AI Studio вообще не поддерживает MCP» нельзя использовать
как установленный факт. Доступность этого режима и совместимость с нашим Gate
нужно проверить отдельно. Переключение на Agents не считать выполнением задачи,
если пользователь хочет остаться в обычном веб-чате.
Источник: [Agents in AI Studio playground](https://ai.google.dev/gemini-api/docs/aistudio-agents).

Основная архитектура ниже рассчитана на обычный веб-чат без доступного MCP-коннектора.
Доступ к браузерным вкладкам в этой сессии отсутствует; текущие DOM, редактор,
кнопки Run/Stop и экран возврата function response не исследованы. Имена CSS-классов
и возможность автоматической отправки нельзя считать проверенными.

### Репозиторий

| Уже есть | Как использовать |
| --- | --- |
| `/mcp/v5`, `initialize`, `tools/list`, `tools/call` | Получать действующий контракт и инструменты, не дублировать каталог вручную. |
| Gate, независимые MCP-подключения и назначение агентов | Создать отдельное подключение для расширения; сохранить маршрутизацию и отзыв доступа. |
| Политика инструментов на агенте | Сохранить проверки; при выдаче расширению более узких прав проверять пересечение на Gate. |
| `request_key`, `list_commands`, `poll_command`, `cancel_command` | Продолжать уже запущенный процесс вместо нового запуска после потери ответа. |
| `browser-extension/`, Native Messaging, debugger | Это расширение для управления браузером со стороны MCP. Не превращать его в клиента AI Studio. |
| `internal/buildinfo`, версия в соединении agent ↔ Gate | Проверить при выпуске, использовать реально полученную версию другой стороны. |

Текущий OAuth Gate требует Client Secret и разрешает callback ChatGPT/Gemini.
Готового безопасного входа для отдельного расширения сейчас нет. Простого
добавления адреса расширения в список callback недостаточно.

Текущие ожидающие вызовы Gate находятся в памяти. Постоянного журнала всех
MCP-вызовов для восстановления после перезапуска сервера нет. Идемпотентность
`exec_command` не означает, что все остальные инструменты имеют ту же гарантию.

## 3. Какой способ интеграции выбрать

| Вариант | Решение |
| --- | --- |
| Штатное подключение MCP в нужном режиме AI Studio | Проверить первым. Если действительно доступно без AI-ключей и сохраняет нужный сценарий, использовать его. |
| Встроенный function calling с доступным вводом результата | Проверить прототипом. Выбрать для первой версии только после подтверждения полного цикла через интерфейс. |
| Строгий JSON-запрос в обычном ответе модели | Основной вариант для расширения: не зависит от наличия внешнего tool executor в AI Studio. |
| Перехват внутренних Google RPC/fetch и подмена ответов | Не выбирать: привязка к внутреннему протоколу сайта и лишний доступ к данным аккаунта. |
| Собственный чат поверх Gemini API | Не подходит: требует AI-ключ и меняет запрошенный сценарий. |
| Локальный HTTP-сервер или новый Native Messaging host | Не нужен для первой версии: Gate уже доступен по HTTPS. Рассматривать только при отдельном требовании работать без Gate. |

Content script умеет читать и менять DOM страницы, но живёт в изолированном
JavaScript-контексте. Поэтому транспорт к Gate и токены размещаются в service
worker, а работа с сообщениями и редактором — в content script.
Источник: [Chrome content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts).

Основной режим — текстовый протокол. Если этап исследования докажет, что нативный
function calling полностью работает через UI, заменить только адаптер сообщений.
Не разрабатывать и не сопровождать два режима в первом выпуске одновременно.

## 4. Что увидит пользователь

1. Открывает обычный чат AI Studio и боковую панель расширения.
2. Подключается к своему Gate, выбирает компьютер и разрешённые инструменты.
3. Включает WebCodex для этого диалога. Расширение показывает инструкцию для модели
   и каталог инструментов; пользователь может проверить их перед добавлением.
4. Пишет обычную задачу, например: «Прочитай README проекта и предложи исправление».
5. Модель выдаёт запрос инструмента. Панель показывает инструмент, компьютер,
   аргументы и состояние выполнения; операции записи/команды требуют разрешения
   в пределах выбранного режима доступа.
6. После выполнения результат появляется в панели и отправляется реальным
   сообщением в исходный чат. AI Studio получает его в контексте и продолжает.
7. Пользователь может приостановить цикл или отключить мост.

Нарисованная поверх страницы карточка результата не считается возвратом модели.
Нужно проверить, что отправленное сообщение появилось в истории сайта и повлияло
на следующий ответ. В текстовом режиме это сообщение роли пользователя с явной
меткой результата инструмента, а не настоящий API `functionResponse`.

Если редактор не пуст, идёт генерация, сменился диалог или интерфейс не распознан,
сохранить результат и поставить цикл на паузу. Не стирать пользовательский текст
и не нажимать Run вслепую. Ручной режим «вставить результат» нужен как восстановление;
полностью автоматический цикл считается готовым только после отдельной проверки.

## 5. Протокол между моделью и расширением

В начале включённой сессии модель получает правила, описание разрешённых
инструментов из Gate, выбранный компьютер и текущую метку шага. Существующие
инструкции пользователя сохраняются; не заменять их целиком. Если каталог не
помещается в разумный объём, пользователь выбирает меньший набор инструментов.
Названия, обязательные параметры и предусловия выбранных инструментов не обрезать.

В первом выпуске — один вызов за один ответ модели, без параллельных групп.
Полный ответ с вызовом содержит только блок `webcodex-call` с одним JSON-объектом.
Обычный ответ без такого блока завершает цикл.

Пример запроса:

````text
```webcodex-call
{
  "v": 1,
  "turn": "step-example",
  "name": "read_file",
  "arguments": {
    "path": "C:\\projects\\demo\\README.md"
  }
}
```
````

`v` — версия нашего текстового формата, пока `1`. `turn` — метка текущего шага,
которую выдаёт расширение; `step-example` приведена только как пример.
`name` — точное имя разрешённого MCP-инструмента. `arguments` — его параметры
по схеме из Gate. Путь в примере относится к демонстрационному проекту; в реальном
запросе модель использует согласованный с пользователем абсолютный путь.

Выбранный `agent_id` добавляет расширение. Запрос модели на другой компьютер
отклоняется; `list_agents` остаётся специальной операцией без аргументов.
Для инструментов с обязательным `request_key` расширение создаёт ключ до отправки,
фиксирует его вместе с окончательными аргументами и сохраняет при восстановлении.

Пример сообщения с результатом:

```json
{
  "type": "webcodex-result",
  "v": 1,
  "turn": "step-example",
  "operation_id": "operation-example",
  "name": "read_file",
  "result": {
    "content": [{"type": "text", "text": "Содержимое демонстрационного файла"}],
    "isError": false
  },
  "next_turn": "next-step-example"
}
```

`operation_id` — идентификатор сохранённого вызова на Gate, `result` — фактически
полученный результат MCP с сохранением `isError`, текстовых блоков и доступных
структурированных данных. `next_turn` — новая метка следующего шага. Все значения
с окончанием `example` — иллюстрации, реальные идентификаторы создаются программой.
Транспортные ошибки передаются отдельно от успешного результата; не выдумывать
вывод инструмента. Неподдерживаемые типы результата обозначать явно.

Правила распознавания:

- Читать только новый, законченный ответ модели в привязанном диалоге после
  включения моста. Не сканировать всю историю, пользовательские сообщения,
  размышления модели, цитаты, поисковые результаты и содержимое файлов.
- Ожидать закрытия блока и подтверждённого окончания генерации. Тишина DOM
  в течение нескольких секунд сама по себе не доказывает завершение.
- Проверять формат, текущую метку шага, имя, схему аргументов, размер и выбранный
  набор инструментов. Два блока, неизвестные поля конверта, неполный JSON или
  старый шаг означают остановку с понятной ошибкой.
- Не исполнять произвольный JavaScript, Markdown-команды и shell-текст из обычного
  ответа. Shell разрешён только как явно разрешённый вызов `exec_command`.
- Метка шага и роль DOM-элемента помогают избежать случайного запуска примера,
  но не аутентифицируют модель и не защищают от prompt injection. Решающее
  ограничение — права Gate и разрешение пользователя на операции.

## 6. Границы компонентов

Новое расширение разместить в `ai-studio-extension/`, независимо от
`browser-extension/`. Повторно использовать только подходящие небольшие приёмы
хранения/тестирования; не переносить debugger и управление чужими вкладками.

| Компонент | Ответственность |
| --- | --- |
| Адаптер AI Studio в content script | Определение текущего диалога, нового ответа и окончания генерации; вставка результата и проверка его отправки. |
| Чистый разборщик протокола | Формат, ограничения, схемы и отделение запроса от обычного текста; тестируется без сайта. |
| Service worker | Проверка отправителя, авторизация, создание/чтение операции на Gate, сохранение состояния. |
| Боковая панель | Выбор Gate/агента/инструментов, разрешения, статусы, результат, Pause и Stop. |
| Небольшой адаптер на Gate | Авторизация расширения, сохранение операции, выполнение через общую MCP-маршрутизацию. |
| Существующий агент | Реальное выполнение инструментов; без логики Google и без AI-ключей. |

Все привязки к DOM AI Studio держать в одном модуле. Проверять семантические
признаки и уникальность найденных элементов. При изменении сайта безопасно
приостанавливать мост, а не пытаться нажать похожую кнопку.

Разрешения расширения: `storage`, `sidePanel`, `identity`; content script только
на `https://aistudio.google.com/`. Для сети — доступ к конкретному выбранному Gate,
запрашиваемый при подключении. Для произвольного домена Gate допустимо объявить
шаблон optional host permission, но фактически выдавать разрешение только одному
выбранному origin. Без `debugger`, `cookies`, `nativeMessaging`, `<all_urls>` и
доступа ко всем вкладкам. Если прототип докажет необходимость дополнительного
разрешения, сначала зафиксировать конкретную причину.

Запросы к Gate идут из service worker: content scripts сохраняют ограничения
сетевого origin страницы. Не создавать универсальное действие «запросить любой
URL из страницы». Источник: [Cross-origin network requests](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests).

## 7. Авторизация к Gate без секретов в странице

Выбрать OAuth Authorization Code + PKCE S256 для отдельного типа публичного
клиента расширения. Использовать `chrome.identity.launchWebAuthFlow` и точный
callback, полученный расширением. Эти Chrome API поддерживают вход к внешнему
провайдеру; AI-ключ для этого не нужен.
Источник: [Chrome identity](https://developer.chrome.com/docs/extensions/reference/api/identity).

Нужные изменения Gate:

1. Добавить отдельный тип MCP-клиента расширения с точным зарегистрированным
   redirect URI и явным набором инструментов. Не разрешать все адреса
   `chromiumapp.org` и не отменять Client Secret для прежних клиентов.
2. Для нового публичного клиента обязательно требовать вход администратора Gate
   и явное подтверждение выдачи доступа на странице Gate с защитой от CSRF.
   Сейчас authorize выдаёт код после проверки Client ID/PKCE без такого согласия:
   это нельзя переносить на клиент без секрета. PKCE не заменяет вход пользователя.
3. Сохранить проверку одноразового кода, redirect URI, срока действия, PKCE и
   `state`; `state` проверяет расширение. Admin-пароль вводится только на Gate.
4. Ограничить вызовы пересечением: разрешённые агенты MCP-подключения, инструменты
   публичного клиента, действующая политика выбранного агента. Для нового клиента
   пустой список инструментов означает отсутствие разрешений.
5. Проверять права и при получении сохранённого результата. Отзыв подключения или
   исключение агента закрывает последующий доступ. Расширение набора прав требует
   нового согласия и отзыва прежней выдачи доступа.
6. Токен хранить в `chrome.storage.session`, доступном только доверенным контекстам;
   для постоянных настроек использовать storage с ограничением доступа content
   scripts. Не использовать синхронизацию Chrome для секретов. После перезапуска
   браузера или истечения токена — повторный вход и пауза до восстановления.

Первый выпуск обходится без refresh token и нового способа хранения долговечных
секретов. В Gate остаются прежние клиенты и сценарии входа. Минимальные права
для первого подключения — чтение в демонстрационном проекте.

Каталоги сейчас ограничены на агенте, а не индивидуально на каждом MCP-клиенте.
Отдельное подключение само по себе не создаёт отдельную файловую песочницу.
Для строгой изоляции использовать отдельный агент и права ОС. `exec_command`
работает с правами пользователя агента; allowed roots не ограничивают shell.

## 8. Устойчивость и отсутствие повторного выполнения

Chrome может завершить фоновый service worker, в том числе при долгом ожидании
сети. Держать единственный экземпляр состояния в глобальных переменных нельзя.
Источник: [Service worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle).

Поэтому после доказательства работы DOM-прототипа добавить на Gate тонкий
асинхронный адаптер, а не держать длительный MCP HTTP-вызов внутри worker.
Не создавать второй исполнитель, брокер сообщений или отдельный daemon.

Предлагаемый контракт:

| Запрос | Назначение |
| --- | --- |
| `POST /bridge/v1/operations` | Принять один проверенный `tools/call`, записать операцию и быстро вернуть её ID. |
| `GET /bridge/v1/operations/{id}` | Вернуть состояние и, если готов, сохранённый результат. `{id}` — ID операции, выданный Gate. |

Для `initialize`, каталога и списка агентов использовать существующий `/mcp/v5`.
Новый адаптер нужен для сохранения выполнения, а не для замены протокола MCP.
Общую проверку и маршрутизацию выделить из обработчика MCP ровно настолько,
чтобы новый путь не обходил авторизацию, выбор агента, tool policy и контракт v5.
Не обращаться из нового endpoint напрямую к runtime в обход этих проверок.

Состояния на Gate: `accepted`, `dispatching`, `completed`, `failed`,
`outcome_unknown`. Последнее означает, что факт применения операции установить
не удалось. До отправки агенту Gate надёжно сохраняет `dispatching`.
После перезапуска незавершённые операции не отправляются автоматически ещё раз:
даже если процесс мог оборваться до реальной отправки, безопаснее показать
неизвестный исход, чем повторить изменение.

В SQLite хранить владельца MCP-подключения, выбранного агента, ключ операции,
хеш окончательных аргументов, статус, ограниченный результат и время истечения.
Повтор того же ключа и аргументов возвращает прежнюю операцию. Тот же ключ
с другими аргументами отклоняется. Уникальность обеспечивает ограничение базы,
а не проверка в памяти. Рабочий вызов имеет собственный ограниченный deadline
и не зависит от закрытия HTTP-запроса создания операции.

В расширении сохранять привязку к вкладке и диалогу, экземпляр сессии, шаг,
снимок запроса, ключ/ID операции и состояние доставки результата. Новый ответ
с теми же аргументами не обязательно является повтором: одинаковое чтение
в следующем шаге законно. Подавлять дубли по сохранённому шагу/операции.

Дополнительные правила:

- Перезагрузка вкладки не запускает старые блоки из истории. Восстановление
  требует сопоставить сохранённую сессию и конкретный диалог.
- При неизвестном исходе отправки сообщения в AI Studio сначала искать его в
  истории по ID операции. Если нельзя доказать доставку или её отсутствие,
  остановиться; не отправлять результат повторно автоматически.
- Закрытие панели, вкладки или сети не означает отмену команды на компьютере.
  Pause запрещает новые вызовы и отправки. Stop дополнительно пытается отменить
  известную командную/браузерную сессию штатным инструментом; успешную отмену
  показывать только после подтверждения. Для обычного файлового вызова откат
  и гарантированная отмена не обещаются.
- Для процесса после `exec_command` использовать `session_id` и `poll_command`
  с сохранёнными смещениями; `running` не равно успешному завершению задачи.
- Ограничить запрос 64 KiB, автоматически отправляемый текст результата 32 KiB,
  один активный вызов на диалог, цикл десятью вызовами или пятью минутами до
  предложения продолжить. Это начальные проверяемые пределы, не оценка токенов.
- Полный ответ хранить ограниченно на Gate, показывать в панели. При обрезке
  обозначать это явно; хеши, обязательные поля и предусловия редактирования
  не обрезать. При недостатке данных запросить меньший диапазон инструмента.
- Начальный срок результата — 24 часа с ограничением общего размера; ключи
  завершённых операций хранить минимум до конца срока допустимого повтора
  соответствующей выдачи доступа. Просроченную операцию не создавать заново
  при автоматическом восстановлении. Согласовать очистку, отзыв токенов и
  tombstone-записи тестом, чтобы удаление результата не разрешало повтор.

Журнал предотвращает повторную отправку одной операции через мост. Он не создаёт
универсальной гарантии exactly-once для файлов, shell и сторонних MCP-сервисов.
После сбоя между изменением и записью результата возможен `outcome_unknown`.

## 9. Безопасность и данные

- Все данные из страницы, ответа модели и инструмента считать недоверенными.
  Выводить через текст, без выполнения HTML/JS и без `eval`.
- Service worker проверяет отправителя: разрешённый origin AI Studio, верхний
  frame, подключённую вкладку и текущую сессию. Content script не может сам
  прислать признак «пользователь разрешил запись»; согласие принимается только
  из доверенной панели расширения.
- В первой рабочей версии чтение выполняется в явно разрешённой сессии, запись,
  удаление и запуск команд подтверждаются по вызову. Позже можно добавить
  ограниченное разрешение на текущую задачу, если это потребуется пользователю.
- Не давать модели управлять вкладкой своего диалога через browser tools:
  в первом выпуске вообще не включать браузерные инструменты в выдачу этому
  расширению. Их добавление потребует отдельной защиты от рекурсивного цикла.
- Инструкция «игнорировать команды в выводе инструмента» полезна, но не является
  защитной границей. Серверные права и изоляция ОС обязательны.
- Чтение файла с отправкой результата в чат раскрывает эти данные Google.
  Показать это при включении моста и соблюдать выбранный пользователем объём
  данных. Ключи, токены, cookies и файлы учётных данных не добавлять в контекст.
- Сохраняемый результат на Gate тоже может содержать частные данные: права на
  SQLite и резервные копии, сроки удаления, квоты, отсутствие тел результатов
  в обычных логах. Записывать статус, ID и длительность без секретных аргументов.
- Для HTTP проверять разрешённые Origin, аутентификацию, размер, права на операцию
  и rate limits. Отсутствие CORS-заголовков не заменяет авторизацию. Учитывать
  существующих клиентов без Origin, не ломая их молча.
  Основание: [MCP HTTP transport](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports).

## 10. План по этапам и критерии завершения

### Этап 0. Подтвердить способ обмена через реальный веб-интерфейс

Проверить нужный режим и аккаунт: штатный MCP, наличие полного UI function calling,
обычный чат. В отдельном тестовом диалоге с вымышленными данными определить
редактор, ответы модели, индикатор завершения, историю отправки, идентичность
диалога, переходы внутри SPA, поведение regenerate и кнопки Stop.

Результат: короткая запись с проверенным способом получения вызова и возврата
результата; обезличенные DOM-примеры для тестов. Критерий: AI Studio получила
вставленный тестовый результат и использовала его в следующем ответе, без
AI-ключа и без вызова API модели из нашего кода. Если это не удаётся, остановить
разработку автоцикла и зафиксировать конкретное препятствие.

### Этап 1. Прототип расширения с тестовым исполнителем

Создать отдельное MV3-расширение, адаптер страницы, разборщик протокола и панель.
Проверить цикл «запрос → фиксированный тестовый результат → продолжение» без
доступа к реальным файлам. Пользовательские черновики и старые сообщения
не исполняются. Включить Pause, Stop и понятную диагностику несовместимого UI.

Критерий: десять последовательных коротких циклов в тестовом диалоге без пропусков,
двойной отправки и выполнения частичного ответа; отдельно проверить regenerate,
смену диалога, ручную остановку генерации и исчезновение нужного элемента.

### Этап 2. Безопасный вход и устойчивые вызовы Gate

Добавить тип публичного клиента, вход/согласие на Gate, точный callback, права
инструментов и две операции асинхронного адаптера. Сохранить совместимость старого
OAuth. Реализовать миграцию SQLite и восстановление неизвестного исхода.

Критерий: посторонний клиент не получает доступ, отозванные права действуют сразу;
обрыв создания/чтения операции и остановка worker не повторяют вызов. Сбой Gate
после отправки агенту отображается как неизвестный исход.

### Этап 3. Рабочее чтение через MCP

Подключить `initialize`, каталог, выбор агента и минимальный набор чтения:
`list_allowed_roots`, `list_directory`, `read_file`, затем `search_files`/`find_files`
по фактическому каталогу. Подтвердить полный путь через наш Gate и агент.

Критерий: задача «изучи небольшой демонстрационный проект и объясни устройство»
выполнена из AI Studio без ручного копирования каждого результата. Сохранение
ответа только в панели критерию не соответствует.

### Этап 4. Редактирование и команды для задач разработки

Добавить явное включение `write_file`/`edit_file` и необходимых операций с путями;
показывать пользователю изменение и предусловия. Сохранить SHA-256 и атомарные
операции существующего агента. При разрешённом shell добавить `exec_command`,
`poll_command`, `list_commands`, `cancel_command` и отображение финального exit code.

Критерий: AI Studio читает тестовый файл, предлагает и применяет согласованную
правку, запускает проверку, получает её фактический результат. При потере ответа
команда не стартует второй раз. Конфликт хеша не приводит к перезаписи.

### Этап 5. Приёмка и отдельная поставка

Выполнить проверки ниже, собрать пакет расширения и нужные бинарники; подготовить
простую инструкцию установки готового комплекта и отдельную инструкцию сборки.
После каждого законченного этапа проверить изменения, создать отдельный коммит
с обозначением части проекта в скобках и сразу отправить в соответствующую ветку.
Черновой прототип не представлять как готовую поставку.

Критерий: пользователь устанавливает готовое расширение, входит только на Gate,
включает мост для диалога и выполняет полный сценарий без AI-ключей.

## 11. Обязательные проверки реализации

| Уровень | Что должно быть проверено |
| --- | --- |
| Разборщик | Обычный текст, пример в цитате, неверный JSON, лишний блок, старый шаг, неизвестный инструмент, неверные/слишком большие аргументы. |
| Адаптер UI | Поток ответа, остановленная генерация, regenerate, виртуализация истории, новый чат при прежнем URL, ручной черновик, локализация, отправка и проверка результата. |
| Авторизация | PKCE/state/callback, согласие после входа, CSRF, запрет выдачи без секрета старому клиенту, просроченный/отозванный токен, запрет чужого агента и результата. |
| Вызовы | Одинаковый ключ, конфликт аргументов, два одновременных запроса, worker restart, Chrome restart, Gate restart на разных стадиях, очистка результата и защита от повторного запуска. |
| Разработка | Конфликт SHA, ошибочный путь, не-UTF-8 файл, running/exit code, большие логи, разрыв связи и восстановление session_id, отмена процесса. |
| Совместимость | Текущие MCP v3/v4/v5, существующий OAuth ChatGPT/Gemini, независимое browser-extension, Windows-агент и поддерживаемый Linux-агент. |
| Конфиденциальность | Токен недоступен странице/content script, нет секретов в логах/чате, отключённый диалог не читается мостом, HTML результата не исполняется. |

Для чистого протокола и фоновой логики использовать существующий подход Node
assert/test без нового фреймворка ради нескольких функций. Для Gate — Go-тесты
с существующим тестовым окружением. Автотест DOM на сохранённом примере не заменяет
живую проверку в AI Studio.

## 14. Граница первого выпуска

Первый полный результат — обычный веб-чат AI Studio выполняет через наш MCP
цепочку чтения, согласованной правки и проверки небольшого проекта без AI-ключей;
вызовы и результаты видны пользователю, опасный повтор после сбоя исключён
остановкой при неизвестном исходе.

Не включать в первый выпуск другие AI-сайты, произвольные внешние MCP-серверы,
параллельные группы инструментов, изображения/видео/бинарные вложения, доступ
к cookies, управление самим диалогом через browser tools и публикацию в Chrome
Web Store. Мультимодальные результаты требуют отдельной проверки загрузки через
веб-интерфейс; текст с base64 не заменяет видимое модели изображение.

Главные оставшиеся риски — изменение интерфейса AI Studio, соблюдение моделью
текстового формата и ограничения сайта. Их нельзя устранить документацией;
первым результатом разработки должен стать проверенный живой цикл обмена.
