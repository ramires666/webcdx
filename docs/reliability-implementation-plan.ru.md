# План повышения устойчивости AI Studio Bridge

Подготовлен 14 ноября 2026 года по состоянию репозитория `231db7c`.
Документ предназначен для последовательной реализации и проверки изменений.

Этап 0 завершён. Контракты, корпус и исходные проверки зафиксированы
в [карте контрактов](reliability-contracts.ru.md). Этапы 1–11 ожидают реализации.

## Результат, который должен получить пользователь

Обычный запрос в чате приводит к выполнению разрешённой задачи с сохранением
результатов при перерисовке страницы, задержках и переподключениях.
Небольшие дефекты оформления ответа восстанавливаются локально.
Автоматические дополнительные вопросы модели из-за синтаксиса имеют бюджет ноль.

Модель выдаёт короткий заголовок с параметрами и сырое содержимое файла либо
команды. Расширение формирует внутренний JSON и служебные идентификаторы.
Случайный маркер помогает распознавать рамку ответа и принадлежность сеансу.
Журнал агента сохраняет факты исполнения независимо от доступности вкладки.

Необходимые обмены с результатами инструментов сохраняются. Если ответ модели
зависит от ещё неизвестного ей результата чтения или команды, этот результат
нужно передать в диалог. Метрика лишних вопросов считается отдельно.

Основания для плана находятся в анализе истории, архитектурном предложении
и проекте нового синтаксиса. Этот документ задаёт порядок их реализации.
[Анализ](recent-push-reliability-audit.ru.md),
[архитектура](reliability-architecture-proposal.ru.md),
[протокол](model-reply-protocol-v2.ru.md).

## Принятые решения

| Область | Решение |
| --- | --- |
| Внешний сценарий | Веб-чат AI Studio с существующей авторизацией и согласованными разрешениями |
| Синтаксис модели | Короткий заголовок и отдельное сырое тело для основных строковых инструментов |
| Внутренний запрос | Существующее представление инструмента и аргументов с проверкой схемы |
| Старые ответы | Совместимый входной адаптер JSON v1 с общей последующей проверкой |
| Маркер | Расширение создаёт случайное значение один раз для нового сеанса |
| Восстановление оформления | Ограниченные локальные правила с проверкой сохранности значений |
| Ошибка разбора | Сохранённый исходник и причина в панели при нуле автоматических переспросов |
| Координация | Один активный координатор с явными переходами и проверкой актуальности событий |
| Исполнение | Устойчивый идентификатор и журнал фактов у агента |
| Доставка в чат | Отдельное состояние с положительным подтверждением принадлежности результату и диалогу |
| Большие данные | Отдельные артефакты и вложения с проверкой целостности |
| Выпуск | Проверенный комплект конкретного исходного коммита с версиями и контрольными суммами |

Формат сырых данных, локальное восстановление, координатор и журнал применяются
в существующих компонентах. Используются имеющиеся схемы, очереди, JSON-библиотеки,
хранилища операций и упаковочные скрипты.

## Этап 1. Убрать автоматические переспросы из обработки ошибки разбора

2. Передачу `call_validation` в чат сделать явным однократным действием пользователя.

3. Отображать в панели причину, доступный исходник и возможность повторного

4. При неизменном ответе кэшировать результат анализа. При продолжающейся

5. Сохранить необходимую доставку результатов реальных инструментов и обычный

## Этап 2. Зафиксировать простой синтаксис и правила данных

Для основных инструментов принять заголовок с параметрами по строкам.
Вариант с маркером имеет следующий вид.

```text
HELPER_Q7K2 write_file
path: W:/project/page.html
if_absent: true
---
<div title="Привет">Содержимое файла</div>
END_Q7K2
```

`Q7K2` показан в сокращённом виде. Расширение создаёт настоящее случайное значение
и передаёт его в контекст сеанса. `write_file` выбирает инструмент, `path` задаёт
путь на Windows-агенте, `if_absent: true` разрешает создание отсутствующего файла.
Первая строка `---` завершает заголовок. Для этого инструмента тело становится
значением `content`. `END_Q7K2` обозначает внешнюю завершающую рамку.

1. Описать начало и конец служебного участка, допустимое пояснение снаружи,
   пробелы в заголовке, параметры без тела и правила пустого содержимого.
2. Параметр разделять по первому двоеточию. Тип и допустимость значения брать
   из действующей схемы инструмента. Сохранить двоеточия и пробелы в самих путях.
3. Для `write_file` использовать сырое `content`, для текстового варианта
   `exec_command` использовать сырое `command`. Связь задаётся небольшой явной
   таблицей полей на основе имеющихся схем.
4. Определить сохранение LF, CRLF, завершающих переводов строки и пустого файла.
   Разделители рамки исключаются по формальным границам. Содержимое тела
   сохраняется без `trim`, замены слешей и исправления кавычек.
   Завершающую рамку распознавать на внешней границе исходника блока.
   Такой же текст внутри тела остаётся содержимым.
5. Для вложенных аргументов и массивов сохранить явно обозначенный структурированный
   участок. Он проходит имеющуюся проверку схемы и общий адаптер совместимости.
   Большие строковые значения выносить в сырое тело по согласованному контракту.
6. Определить поведение при двух служебных блоках, повторных параметрах,
   неизвестном инструменте и конфликте источников. Эти случаи сохраняются
   как неоднозначные до разрешения причины.
7. Генерировать показываемые модели поля и примеры из действующих схем
   и таблицы соответствия сырого тела. Внутреннее представление сохраняет
   существующие `name` и `arguments`.

**Готовность этапа** требует примеров и ожидаемого представления для каждого
инструмента из этапа 0, включая `argv`, вложенные замены и пустые строки.

## Этап 3. Получать точный источник ответа из DOM

1. В адаптере сохранять принадлежность участков текущему ответу, границы кода,
   текстовые узлы, BR и видимые заголовки. Сохранять ревизию наблюдения.
2. Поддержать исходник PRE/CODE, соседние блоки с отдельным заголовком языка
   и литеральный Markdown, который отобразился как обычный текст.
3. Исключать мысли, скрытые копии, кнопки Copy и старые сообщения на этапе
   определения источника. Вложенные обёртки одного участка учитывать по происхождению.
4. Различать две самостоятельные команды и две обёртки одной команды.
   Совпадение текста двух разных участков сохраняет их отдельность.
5. Завершение принимать по совокупности состояния генерации, стабильного источника
   и полноты рамки. Непосредственно перед допуском перепроверять ревизию.
6. На ошибке сохранять понятный результат извлечения. Это позволит исправлять
   адаптер по сохранённому примеру и повторно анализировать уже полученный ответ.

Изменения сосредоточить в существующем адаптере и его контракте с content.
Проверки настоящего Chrome дополняют имеющийся упрощённый DOM-стенд.
[Адаптер](../ai-studio-extension/studio-adapter.js),
[DOM-стенд](../ai-studio-extension/test-fixtures/studio-dom.cjs),
[Chrome-проверка](../ai-studio-extension/real-studio-dom.test.cjs).

**Готовность этапа** требует одинаковых аргументов и содержимого во всех
поддержанных вариантах отображения, включая подсветку по отдельным токенам.

## Этап 4. Реализовать маркер и жизненный цикл привязки чата

1. Создавать маркер платформенным генератором случайных значений с энтропией
   порядка 128 бит. Выбрать ASCII-алфавит, удобный для копирования моделью.
2. Хранить маркер вместе с локальной идентичностью диалога, поколением ответа
   и состоянием привязки. Сохранение URL и перерисовка сохраняют прежний маркер.
3. Для нового диалога создавать новую запись. Для повторного открытия сопоставлять
   локальную запись с текущим документом и подтверждённым контекстом.
   Скопированную историю и дубликат диалога проверять отдельно.
4. Общий preset `Helper` содержит общую инструкцию формата. Для маркера проверить
   изолированный контекст конкретного чата. Первым вариантом проверить добавление
   сессионного блока в первое уже отправляемое сообщение с сохранением текста
   пользователя. Проверка двух вкладок должна подтвердить изоляцию.
5. Доставка маркера использует уже необходимый обмен. Число дополнительных
   запросов подтверждения маркера равно нулю.
6. Маркер распознавать в служебных позициях. Его появление внутри файла,
   примера кода или старой истории остаётся данными.
7. При пропущенном маркере разрешать запасной разбор только при однозначной
   независимой привязке свежего ответа. Явный маркер другого сеанса сохраняет
   конфликт. Длинный идентификатор операции, номер шага и контрольные суммы
   формируются на нашей стороне.

**Готовность этапа** требует проверок нового, сохранённого, дублированного
и повторно открытого чата, двух вкладок, общего preset и перезапуска расширения.
Неполное повторение маркера обрабатывается локально по установленным правилам.

## Этап 5. Реализовать разбор и локальное восстановление

1. В общей точке разбора принимать новый текстовый формат и существующий JSON v1.
   Оба входа приводить к текущему представлению инструмента и аргументов.
2. Сначала проверять точный формат и число самостоятельных кандидатов.
   Затем применять ограниченные правила восстановления оформления.
3. Для заголовка разрешить однозначные пробелы, допустимый регистр булевых
   литералов и заранее описанные эквивалентные разделители.
4. Для JSON v1 использовать имеющиеся `jsonc-parser` и `jsonrepair` с проверкой
   происхождения значений. Допускать восстановление пунктуации, завершающих
   запятых и известных вариантов кавычек при единственном смысле.
5. Проверять сохранность строк, чисел, типов, порядка массивов и связи значений
   с полями. Проверка только последовательности строк должна быть усилена.
6. Для путей учитывать тип поля и ОС агента. Буквальную Windows-запись
   восстанавливать по отдельному правилу, сохраняя команды и файлы как данные.
7. Восстановление заключительной скобки или рамки связывать с надёжной границей
   полного источника. Отсутствующие значения и байты сохранять как неполные данные.
8. Каждый принятый результат снабжать локальным списком применённых правил.
   При разных допустимых аргументах сохранять неоднозначность.
9. Ограничить число вариантов и работу. Сырые файлы исключить из перебора
   исправлений. Результат на неизменном источнике кэшировать.

Переиспользуются нынешние анализатор, валидация схемы и установленные библиотеки.
Проверки точного, восстановленного и отвергнутого ввода достигают одной точки
регистрации операции.
[Протокол](../ai-studio-extension/protocol.js),
[JSON-восстановление](../ai-studio-extension/json-recovery.test.cjs),
[сырые файлы](../ai-studio-extension/raw-file.test.cjs).

**Готовность этапа** требует прежних данных на всех разрешённых искажениях,
нуля ложных исполнений на негативном корпусе и нуля автоматических переспросов.

## Этап 6. Согласовать переходы координатора

1. Описать владельца каждого факта и таблицу разрешённых переходов.
   У исполнения операции, доставки результата и доступности страницы свои состояния.
2. Переходы оформить чистой функцией текущего состояния и события с результатом
   в виде нового состояния и намерений внешних действий.
3. Переиспользовать существующую последовательную очередь `enqueue`.
   Сохранённые метаданные и намерение действия фиксировать вместе до отправки.
   Для связанных записей использовать транзакцию локального хранилища с проверкой
   восстановления после обрыва. Выбор конкретного хранилища подтвердить на этапе 0.
4. Проверять актуальность поколения диалога, ответа, координатора и редакции
   разрешений перед новым действием и после каждого асинхронного ожидания.
5. Старое подтверждение доставки должно относиться к своей операции и поколению.
   Оно сохраняет независимость от ожидания более свежего ответа.
6. Пауза пользователя и отзыв разрешения блокируют новые действия. Для уже
   принятой операции сохраняются опрос состояния и поддерживаемая отмена.
7. Восстановление определять кодом причины и типом действия. Человекочитаемый
   текст ошибки использовать для отображения.
   Сохранённые предпочтения, текущую операцию и редактируемые поля панели
   обновлять по их ревизиям. Проверить одновременные опросы, ввод пользователя
   и повторный вход по существующим сценариям блокировки подключения.
8. Сначала запустить выделенные переходы наблюдателем на тех же событиях.
   Наблюдатель сравнивает решения и сохраняет расхождения без внешних действий.
   После разбора расхождений переключить единственный активный путь исполнения.

**Готовность этапа** подтверждается воспроизводимыми переходами и восстановлением
после перезапуска на границах сохранения, отправки и подтверждения.

## Этап 7. Согласовать сквозной журнал исполнения

1. Развить существующие `studioOperations`, ключи команд и `bridge_operations`
   до общего договора об идентичности операции, аргументах и результате.
2. Агент резервирует операцию до побочного эффекта и сохраняет итоговый результат.
   Повтор того же ключа возвращает прежний статус. Другие аргументы дают конфликт.
3. Область ключа учитывает клиента, источник и исполнителя. Сохраняется разделение
   локальных и Gate-запросов и их командных историй.
4. Gate хранит факты приёма и доставки и сверяет завершение со статусом агента.
   Согласовать поля протокола для восстановления уже принятого запроса.
5. При потере ответа восстанавливать статус по прежней идентичности на прежнем
   агенте и транспорте. Переключение резервного маршрута относится к новым операциям
   в согласованном состоянии сеанса.
6. После аварии между побочным эффектом и сохранением подтверждения сохранять
   `outcome_unknown`. Для собственных инструментов использовать проверяемое
   конечное состояние, где оно позволяет безопасное уточнение.
7. Согласовать сроки хранения. Истёкший ключ получает явный статус истечения.
   Восстановление старого запроса сохраняет его историю и прежнюю идентичность.
8. Проверить совместимость старых записей и конкурирующих одинаковых запросов.
   Миграция сохранённых состояний сохраняет действующие права и историю действий.

**Готовность этапа** требует одного побочного эффекта во всех сценариях
повторной доставки с известным результатом и явного статуса неизвестного исхода
в точке, где произвольная внешняя команда допускает такую неопределённость.

## Этап 8. Укрепить артефакты и предусловия операций

1. Использовать имеющиеся вложения и ресурсы как основу хранения больших данных.
   В небольших метаданных сеанса сохранять ссылки, размер, тип и контрольную сумму.
2. Проверять целостность при передаче между агентом, Gate, расширением и файлом
   для загрузки. Для частичных чтений явно сохранять границы фрагмента.
3. Зафиксировать ограничения каждого участка и способ продолжения при их достижении.
   Проверить прежние границы 32 КиБ и 2 МиБ, большие Unicode-данные и очередь.
4. Сохранить результат при закрытии вкладки и переподключении. Повторная загрузка
   использует сохранённый артефакт и подтверждённую привязку.
5. Для файлов опереться на существующие `if_absent`, `expected_sha256` и атомарную
   запись. Проверить одновременные изменения и конфликт с внешним редактором.
   Проверка хеша и фактическая публикация должны иметь согласованную защиту гонок.
   Для проверенной ссылки на ранее прочитанный файл ожидаемый хеш брать
   из сохранённого результата той же ревизии. Это освобождает модель
   от вычисления или повторного копирования контрольной суммы.
6. Для скачиваний, форм и браузерных действий определить проверяемый результат.
   Неопределённый исход сохраняет связь с исходной операцией.
7. Для повторных обращений к уже известным файлам оценить короткие ссылки
   на проверенные артефакты. Если они уменьшают ошибки длинных путей, добавить
   явное разрешение ссылки в путь и ожидаемую ревизию. Ввести их после основного
   синтаксиса и его измерения, сохраняя абсолютные пути для совместимости.

Затрагиваются существующие подготовка вложений, файловые инструменты,
клиенты транспорта и при необходимости передача ресурсов через Gate.
[Вложения расширения](../ai-studio-extension/attachments.js),
[ресурсы агента](../cmd/agent/file_attachments.go),
[файловые инструменты](../cmd/agent/file_tools.go).

**Готовность этапа** требует одинаковых байтов на проверяемой цепочке, сохранения
готового результата при сбое и явного конфликта при изменившемся исходном файле.

## Этап 9. Проверять целые классы последовательностей

Использовать существующие стенды с управляемыми часами, подменой транспорта
и настоящим Chrome. Генератор сценариев хранит начальное значение и минимальную
последовательность сбоя. Проверки добавляются вместе с соответствующей логикой.

| Группа | Обязательные сценарии |
| --- | --- |
| Ответ модели | Проза, кавычки, слеши, пропущенная пунктуация, неверный тип, два вызова, оборванный файл |
| DOM | Разные контейнеры, BR, подсветка, скрытая копия, исчезновение Run, поздние токены |
| Маркер | Пропуск, повреждение, маркер другого чата, копия в файле, два чата и общий preset |
| Сеанс | Сохранение адреса, виртуализация истории, новый чат, одинаковые запросы в разных ответах |
| Конкуренция | Поздний ack, повтор сообщения, новый Run во время проверки инструкций, отзыв согласия |
| Сбои | Перезапуск до отправки, после отправки, после побочного эффекта, до сохранения подтверждения |
| Транспорт | Local, Gate, используемый native-маршрут, потеря ответа, подмена идентичности конечной точки |
| Файлы | Пустой файл, CRLF/LF, Unicode, большие данные, конфликт исходника и восстановление вложения |
| Миграция | Старые v1-ответы, сохранённые операции, старое расширение в открытой вкладке, разные версии сторон |

На каждой последовательности проверять принадлежность актуальному диалогу,
сохранность данных, число побочных эффектов, достижимость результата,
правильность неизвестного исхода и число дополнительных сообщений модели.
Для новой вкладки и ответа одинаковый текст допускает новую намеренную операцию.

**Готовность этапа** требует прохождения исторического и нового корпуса,
воспроизводимости сбоев и отсутствия необъяснённых расхождений наблюдателя.

## Этап 10. Обязательная проверка готового комплекта

1. Расширить существующие сборку и упаковку единым сценарием проверки выпуска.
   Выбор Go-пакетов должен охватывать отслеживаемый код и учитывать локальные
   временные каталоги, выявленные при исходном аудите.
2. Запускать JS-тесты, свежие Go-тесты и vet, затем обязательные для выпуска
   проверки настоящего Chrome и собранных EXE. Пропуск обязательной проверки
   даёт статус незавершённой приёмки с конкретной причиной.
3. Проверять распакованный ZIP, наличие всех подключённых скриптов и библиотек,
   версии manifest, package, content, панели и MCP-клиента.
4. Генерировать строки версии расширения из одного источника. Версии агента,
   Gate и протокола записывать отдельно. Согласовывать поддерживаемые возможности
   при подключении и при восстановлении старого состояния.
5. Проверять стартовые версии агента и Gate, обе полученные версии при соединении
   и повторном подключении, а также старую сторону без переданной версии.
   Использовать предусмотренный маркер «версия не передана».
6. Связать каждый пункт заметок о выпуске со сценарием поведения, включая
   историческую ошибку объявления снятого лимита до изменения кода.
7. Создавать манифест с исходным коммитом, версиями компонентов, контрольными
   суммами готовых файлов и результатом проверок. Публиковать прошедшие приёмку файлы.
8. Добавить автоматические проверки репозитория. Указать набор проверок,
   требуемый для выпуска, и отдельно проверить фактические настройки GitHub.

Скрипты расширяются в существующих местах. Для отдельного выпуска сохраняется
полный отчёт обязательных проверок и происхождение готовых файлов.
[Упаковка](../ai-studio-extension/package.ps1),
[инструкция сборки](../ai-studio-extension/BUILD.ru.md),
[версии](../internal/buildinfo/version.go).

**Готовность этапа** требует воспроизводимого комплекта и полного отчёта
приёмки именно его исходного коммита и готовых файлов.

## Этап 11. Приёмка, включение и откат

1. Провести живой сценарий в тестовом AI Studio с временными файлами.
   Проверить новый чат, чтение, запись, команду, сохранение, следующий ответ,
   вложение и повторное подключение.
2. Отдельно измерить количество сообщений. Локальные исправления и ошибки
   оформления должны давать ноль автоматических переспросов.
3. Включать новую инструкцию после готовности установленного расширения
   и проверки актуального content-скрипта в конкретной вкладке.
4. Сначала включить новый формат для основных инструментов и проверить
   обычные задачи. Затем распространить его на оставшиеся согласованные схемы.
5. Новую координацию включать после сравнения решений наблюдателя. На одном
   сеансе действует один исполнитель внешних действий.
6. Перед откатом сохранить журнал принятых операций, ссылки на результаты
   и поддерживаемое представление состояния. При несовместимой миграции
   завершить обработку известной операции либо сохранить неизвестный исход.
7. Инструкция отката указывает точный совместимый комплект, способ сохранения
   базы Gate и восстановления привязки. Повторный запуск уже принятого действия
   контролируется теми же ключами и журналом.

**Готовность этапа** подтверждается живой приёмкой, проверкой восстановленного
результата после сбоя и выполненным сценарием отката на тестовом комплекте.

## Итоговые критерии приёмки

- Все поддержанные инструменты имеют проверенный способ представления аргументов.
- Новый синтаксис сохраняет содержимое без JSON-экранирования больших строк.
- Исправимые дефекты восстанавливаются локально с прежними аргументами и данными.
- Счётчик автоматических запросов исправления равен нулю.
- Маркер создаётся один раз для сеанса и сохраняется при перерисовке и сохранении.
- Старая история и запоздалые события удерживаются от исполнения в новом контексте.
- Известный результат восстанавливается по прежней операции без повторного эффекта.
- Неизвестный исход отображается явно с доступной историей операции.
- Большие файлы проходят проверку целостности и восстановление передачи.
- Готовый комплект имеет согласованные версии и полный отчёт обязательной приёмки.

Доля восстановленных ответов измеряется на корпусе и при обычной работе.
Обещание конкретного процента улучшения требует этих измерений.
Случайный маркер имеет крайне малую вероятность случайного совпадения,
при этом копирование маркера учитывается моделью привязки. Синтаксически корректный
вызов может содержать ошибочное намерение, поэтому сохраняются проверки доступа,
предусловий и результата. Поведение антибот-защиты определяется сервисом.

## Статус текущего этапа

Выполнена подготовка единого плана на основе кода, тестовых стендов
и ранее согласованных предложений. Проверяются ссылки, примеры, покрытие
требований и согласованность этапов документа.

Реализация этапов 0–11 предстоит. Новый агент для этих улучшений ещё не
скомпилирован. Папка будущего готового комплекта предусмотрена в
`bin/ai-studio-bridge`, готовый EXE агента должен сопровождаться версиями
и отчётом приёмки. Самостоятельная сборка для чтения плана не требуется.
Этот этап требует обновления документации. Применение работающих компонентов
и их перезапуски выполняются по конкретной инструкции будущего выпуска.
