# Предложение: простой текстовый протокол вместо JSON в ответах модели

Дата: 14 ноября 2026 года. Статус: проект, код и рабочий комплект не изменены.
Развивает [архитектурное предложение](reliability-architecture-proposal.ru.md)
с учётом требования пользователя минимизировать обращения к модели.

Реализация синтаксиса, маркеров, восстановления и выпуска описана в едином плане.
[План внедрения](reliability-implementation-plan.ru.md).

## Решение

Изменить основной формат ответа: короткий управляющий заголовок с параметрами
по строкам и отдельное непрозрачное тело. Модель не сериализует весь вызов,
код и пути в JSON. Расширение разбирает простой формат, проверяет его по схеме
инструмента и само строит обычный внутренний JSON-запрос.

Так устраняется необходимость в большинстве проблемных синтаксических действий:
экранировании кавычек и обратных слешей, запятых между полями, балансе JSON-скобок,
представлении многострочного кода одной строкой. Это изменение причины ошибок,
а не только расширение списка способов их исправлять.

Автоматические сообщения «исправь ответ» по умолчанию отсутствуют. Восстановление
оформления выполняется локально над тем же ответом. Неразрешимая неоднозначность
отображается в панели без нового запроса к модели. Пользователь может явно
отправить один запрос исправления, без автоматической цепочки продолжений.

## Какие варианты рассмотрены

| Подход | Что даёт | Ограничение |
| --- | --- | --- |
| Структурированный вызов через официальный канал инструментов | Устраняет необходимость извлекать вызов из обычного ответа | Применим, только если такой канал доступен в нужном веб-сценарии без AI-ключей; наличие здесь не установлено |
| JSON с всё более терпимым восстановлением | Совместим с нынешними ответами | Сохраняет обязанность модели сериализовать данные; повреждённые строковые значения иногда неоднозначны |
| YAML, XML или вызов функции как текст | Меняет характер синтаксиса | Остаются требования к отступам, закрывающим конструкциям, кавычкам или экранированию |
| Короткий заголовок + сырое тело | Убирает вложенную сериализацию для основных инструментов | Нужно точно определить границы блока и обработку сложных вложенных аргументов |

Рекомендация для существующего веб-чата — последний вариант. Официальный
структурированный канал можно рассматривать отдельно при подтверждении его
доступности и соответствия исходным требованиям. Переход к AI API keys или
перехвату закрытых запросов сайта в это решение не входит.

## Предлагаемый формат

Модель выдаёт один блок исходного кода с простым содержимым. Для создания файла:

````text
```helper
HELPER write_file
path: W:/project/index.html
if_absent: true
---
<!doctype html>
<div title="Hello">Привет</div>
<script>const p = String.raw`W:\project`;</script>
```
````

Для команды:

````text
```helper
HELPER exec_command
cwd: W:/project
---
python build.py --title "Hello world"
```
````

Для чтения файла тело не требуется:

````text
```helper
HELPER read_file
path: W:/project/README.md
```
````

Это примеры протокольных сообщений, не инструкции запускать показанную команду.
`HELPER` отмечает управляющий блок; `write_file`, `exec_command` и `read_file`
выбирают инструмент. `path` — путь на агенте, `cwd` — рабочая папка команды,
`if_absent: true` разрешает создать только отсутствующий файл.
Строка `---` один раз отделяет заголовок от непрозрачного тела. Для `write_file`
тело становится `content`, для показанного варианта `exec_command` — `command`.
Это соответствие задаётся контрактом инструмента, а не угадывается по содержимому.
Примеры рассчитаны на Windows-агент; формат путей выбирается для реальной ОС.

Внутренние скобки, кавычки, обратные слеши, HTML, shell-операторы и последующие
строки `---` внутри тела являются данными. Парсер не пытается чинить их или искать
там новые вызовы. Не требуется вычислять длину, хеш или кодировать тело в base64.
Служебные идентификаторы и JSON формирует расширение.

## Точные правила, защищающие данные

1. Управляющий блок выделяется в текущем свежем ответе модели. Пояснение снаружи
   допустимо. Внутри блока после начала тела не бывает служебного послесловия.
2. Заголовок разбирается построчно. Параметр разделяется по первому двоеточию;
   двоеточие диска в значении пути не создаёт новое поле. Кавычки вокруг
   однострочного значения не требуются. Пробелы допустимы в самом значении пути.
3. Типы параметров берутся из схемы, не из догадок. Имена, обязательность,
   допустимые значения и предусловия проверяются перед исполнением.
4. Дублирующийся параметр, неизвестный инструмент или два самостоятельных
   вызова дают неоднозначность; нельзя молча выбрать последний или первый.
5. Тело начинается после перевода строки, завершающего первый разделитель,
   и заканчивается на границе извлечённого исходника блока. Оно не проходит
   `trim`, замену слешей, разбор JSON или исправление кавычек.
6. Внешнее Markdown-оформление является транспортом. Источник кода извлекается
   из текстовых узлов с учётом BR и подсветки; чтение всего ответа через
   `innerText`/`textContent` не заменяет извлечение исходника блока.
7. Если содержимое включает Markdown-ограждения, внешнее ограждение должно быть
   длиннее конфликтующего внутреннего. Это остающееся ограничение транспорта,
   требующее проверки. Если сайт разрушил границы, нельзя обещать восстановить
   отсутствующие исходные данные. Альтернатива чтения допустима только при
   надёжно сохранённом источнике того же ответа, а не через новый запрос модели.

Для редких инструментов со сложными вложенными аргументами не следует сразу
изобретать большой язык с отступами и выражениями. Сохраняется явно обозначенный
структурированный блок аргументов; большие строковые поля по возможности
выносятся в сырые тела по схеме. Конкретный набор таких инструментов нужно
инвентаризировать до реализации универсального формата. Первая версия покрывает
чтение, запись и текстовую команду, а не обещает автоматически выразить любую схему.

## Устойчивый алгоритм приёма

1. Закрепить идентичность ответа и дождаться окончания генерации и стабильного
   извлечения локально. Не отправлять сообщения из-за временно неполного DOM.
2. Найти один управляющий участок. Если заголовок или ограждение отображены
   иначе, проверить другие способы извлечения этого же участка. Вложенные
   обёртки одного участка не считаются несколькими вызовами; разные участки
   не объединяются по совпадению текста.
3. Разобрать заголовок по схеме выбранного инструмента. Сырые строки путей
   и тело не требуют JSON-экранирования. При точном разборе значения сохраняются.
4. Если оформление слегка нарушено, применить ограниченные локальные правила:
   лишние пробелы в заголовке, вид ограждения, однозначные разделители параметров,
   допустимый регистр булевых литералов. Нельзя исправлять имя инструмента
   по похожести или дописывать отсутствующий аргумент.
5. Для сохранённого старого JSON-формата использовать отдельный адаптер ввода:
   терпимый разбор и восстановление пунктуации с проверкой сохранности значений.
   Он выдаёт то же внутреннее представление, а не другую логику исполнения.
6. Проверить отсутствие конкурирующих трактовок, схему, право исполнения,
   актуальность ответа и предусловия операции. Если всё выполнено, расширение
   само сериализует внутренний запрос и регистрирует операцию с устойчивым ключом.
7. При локальном успехе не сообщать модели об исправленном формате. Доставить
   только настоящий результат инструмента обычным способом. При неуспехе
   сохранить исходник и причину в панели без автоматического переспроса.

На неизменном ответе результат разбора кэшируется. Повторное наблюдение
не создаёт новую операцию; локальный поиск ограничен по объёму работы.
Новый текст позволяет снова разобрать тот же ответ. Оборванное тело, потерянные
данные и действительно различные трактовки не исправляются догадкой.

Парсер различает ошибку извлечения, неполный ответ, неверное оформление,
неоднозначность и нарушение схемы. Неопознанная разметка не должна автоматически
объявляться ошибкой модели. Успешная схема не доказывает правильность намерения
модели: проверки доступа и предусловия записи сохраняются.

## Уникальный маркер сеанса: полезное дополнение, не единственная опора

Предложение пользователя генерировать уникальный разделитель при начале чата
полезно для различения служебной рамки и данных. Случайный маркер создаётся
расширением один раз при привязке нового диалога, а не самой моделью. Он не
требует отдельного вопроса, подтверждения модели или нового обмена после
каждой операции. При сохранении адреса и перерисовке того же чата маркер прежний.

Возможная рамка — `HELPER_<маркер> write_file`, параметры, `---`, сырое тело,
`END_<маркер>`. Здесь `<маркер>` обозначает автоматически сформированную
ASCII-последовательность, а не текст, который пользователь должен вводить;
порядка 128 случайных бит достаточно для практически исключённого случайного
совпадения. Это не гарантия невозможности намеренно скопировать маркер.

Начало и конец распознаются только в служебных позициях соответствующего блока,
не поиском подстроки во всём чате. Встреча маркера в примере кода или внутри файла
не создаёт вызова. Закрывающая рамка проверяется на границе блока. Такой способ
полезен как дополнительная граница, когда обычный Markdown содержит вложенные
ограждения; он не восстанавливает байты, уже потерянные при отображении сайта.

Маркер — идентичность сеанса протокола, не аутентификация и не абсолютный ID
интерфейсного чата. Скопированная история, дубликат чата или общий preset могут
перенести его в другой диалог. Поэтому привязка требует сочетания локальной
записи, текущей вкладки/документа и поколения свежего ответа. Маркер не заменяет
защиту от повторного исполнения и не даёт права выполнять старую историю.

Нельзя сделать точное повторение длинной строки единственным условием успеха:
это создаст новый класс ошибок копирования. При отсутствии маркера допустим
обычный `HELPER` только если локальная привязка к одному свежему ответу установлена
независимо и без противоречий. Явный маркер другого сеанса нельзя автоматически
подменять текущим или использовать для перехода в другой чат.
Недостающая завершающая рамка допускает чтение по границе исходника блока
только при надёжно установленной полноте; иначе сохраняется неполный ответ.
Повторный вопрос модели ни один из этих случаев автоматически не создаёт.

В нынешнем `studio-adapter.js` используется именованный preset `Helper`.
Нельзя предполагать, что его содержимое изолировано для каждого диалога.
Общую инструкцию формата и уникальный контекст сеанса следует разделить.
Для маркера нужен подтверждённо локальный контекст чата: например, сессионный
блок, объединённый с первым уже отправляемым пользовательским сообщением,
либо проверенный механизм локальной инструкции. Пользовательский текст
сохраняется. Отдельный обмен «запомни маркер — подтверди» не нужен.

Дополнительные способы уменьшить обязанности модели:

- Не просить её считать номер шага, вычислять хеш, генерировать request ID,
  повторять версию агента или JSON-схему. Это данные расширения.
- Для известных файлов/артефактов можно выдавать короткую локальную ссылку,
  которую расширение разрешает в ранее проверенный объект. Это уменьшает
  повтор длинных путей; неизвестные ссылки нельзя исправлять по похожести.
- Шаблон ответа для инструмента получать из его схемы, чтобы инструкция,
  парсер и валидатор не расходились. Модель видит только необходимые поля.
- Принимать ограниченные эквивалентные способы оформления на входе, но
  преобразовывать их в одно внутреннее представление и одну логику исполнения.

Рекомендация — простой заголовок и сырое тело как основа; маркер сеанса как
дополнительная рамка и признак происхождения; локальная привязка и журнал
операций как обязательная защита. Уникальное слово само по себе не решает
экранирование, повреждение DOM, неполные данные или неверный выбор инструмента.

## Как не усложнить задачу модели

В системной инструкции показывается один рекомендуемый формат для выбранного
инструмента. Поддерживаемые запасные варианты не перечисляются как равноправные
требования. Поля формата и шаблоны генерируются из согласованного контракта;
инструкция не переустанавливается после каждого изменения DOM.

Одна пользовательская реплика не должна порождать дополнительные обмены
ради запятых или кавычек. Чтение результата инструмента моделью может требовать
следующего необходимого обмена; формат сам не устраняет эту зависимость.
Автоматический текущий `call_validation` при ошибке парсера предлагается убрать
из поведения по умолчанию, сохранив ручной однократный запрос исправления.

Меньшее число лишних сообщений соответствует требованию сохранять обычный
характер чата. Это не позволяет гарантировать отсутствие срабатываний
антибот-защиты сервиса.

## Проверки и переход

- Сгенерировать корпус ответов с кавычками, Windows-путями, Unicode, shell-кодом,
  HTML, внутренними ограждениями и переводами строк. Проверять полученные значения
  и тело в настоящем Chrome, а не только на плоской строке.
- Мутировать оформление заголовка и DOM. Допустимые изменения сохраняют прежнюю
  операцию; потеря данных, дублирующиеся поля и конкурирующие вызовы не исполняются.
- Во всех проверках считать отправленные в чат сообщения: локальное исправление
  и локальная ошибка дают ноль автоматических запросов исправления.
- Сначала прогнать новый парсер как наблюдателя без исполнения. Затем включать
  формат только после установки совместимого расширения и замены инструкции.
  Старые ответы читаются адаптером совместимости с общей проверкой и дедупликацией.
- Сравнивать долю успешного разбора, ложные исполнения, время обработки и число
  лишних сообщений. Не утверждать заранее процент улучшения без такого сравнения.

Новый синтаксис полностью убирает требования JSON к основным сырым строковым
данным, но не гарантирует отсутствие всех ошибок. Модель всё ещё может выбрать
неверный инструмент, не дописать файл или нарушить границы блока. Эти случаи
остаются явно различимыми и не запускают бесконечный диалог исправлений.

Документ не является выпуском. Агент, Gate и расширение сейчас заменять или
перезапускать не требуется. Новый EXE не скомпилирован; самостоятельная сборка
для ознакомления с предложением не нужна.
