# План переделки WebCodex в локальный MCP для файлов и команд

## 1. Цель

Сохранить существующий публичный Gate, OAuth, SQLite, админку и исходящее
подключение локального агента, но заменить локальный исполнитель на простой и
детерминированный MCP-сервис.

Подключённый ИИ должен видеть только операции с локальными файлами и процессами.
В MCP-ответах не должно быть названий второго ИИ, моделей, reasoning/thinking,
диалоговых потоков или универсального текстового `prompt`.

Итоговая схема:

```text
ChatGPT
   │  MCP Streamable HTTP + OAuth
   ▼
Gate (маршрутизация, политика инструментов, SQLite)
   │  исходящий NDJSON-канал локального агента
   ▼
Local Executor (файлы, поиск, команды, журналы процессов)
   │
   ▼
Локальная файловая система и процессы ОС
```

## 2. Что не входит в задачу

- Локальная или облачная модель внутри агента.
- Интерпретация естественного языка на стороне агента.
- Regex-разбор инструкций пользователя.
- Генерация кода самим агентом.
- Второй агентский цикл, история диалога и `threadId`.
- Новый серверный фреймворк или новый язык программирования.
- Интерактивный терминал/PTY на первой версии.
- Веб-интерфейс для вывода результата инструмента.

Естественный язык понимает ChatGPT. Локальный агент исполняет только явно
структурированный MCP-вызов.

## 3. Что сохраняем

Следующие части уже выполняют нужную работу и должны быть исправлены только там,
где это требуется новым контрактом:

- `cmd/gate`: HTTP-сервер, OAuth, SQLite, админка и маршрутизация агентов;
- `/agent/stream` и `/agent/result`;
- хеширование секретов и ротация токенов;
- раздельные runtime-состояния для разных компьютеров;
- `AllowedTools` и `DeniedTools`;
- корреляция параллельных запросов по внутреннему ID;
- Docker-развёртывание Gate;
- один Go-бинарник локального агента без дополнительных runtime-зависимостей.

Неизвестный инструмент должен возвращать MCP-ошибку и не выполнять никаких
побочных действий.

## 5. Новый публичный MCP-контракт

Список инструментов должен быть небольшим, стабильным и без алиасов.

### 5.1. `read_file`

Вход:

```json
{
  "path": "C:\\projects\\app\\main.go",
  "offset": 1,
  "limit": 500
}
```

- `path` обязателен;
- `offset` — номер первой строки, начиная с 1;
- `limit` — максимальное число строк;
- без `offset` и `limit` действует ограничение максимального размера ответа;
- бинарный файл возвращает понятную ошибку, а не сырые байты;
- ошибка чтения не маскируется пустым результатом.

Аннотации: `readOnlyHint=true`, `destructiveHint=false`.

### 5.2. `write_file`

Вход:

```json
{
  "path": "C:\\projects\\app\\main.go",
  "content": "package main\n"
}
```

- только поля `path` и `content`;
- пустая строка является допустимым содержимым;
- родительские каталоги создаются при необходимости;
- запись выполняется во временный файл в том же каталоге с последующим
  атомарным переименованием;
- при ошибке исходный файл остаётся целым;
- результат содержит нормализованный путь и число записанных байт.

Аннотации: `readOnlyHint=false`, `destructiveHint=true`.

### 5.3. `list_directory`

Вход:

```json
{
  "path": "C:\\projects\\app",
  "max_entries": 1000
}
```

- возвращает имя, тип, размер и время изменения;
- сортирует каталоги и файлы детерминированно;
- ограничивает число записей;
- не выполняет рекурсивный обход: для него ИИ повторно вызывает инструмент.

Аннотации: `readOnlyHint=true`, `destructiveHint=false`.

### 5.4. `search_files`

Вход:

```json
{
  "path": "C:\\projects\\app",
  "pattern": "TODO",
  "glob": "*.go",
  "max_results": 200
}
```

- обычный поиск подстроки по умолчанию;
- отдельный флаг включает регулярное выражение, если это действительно нужно;
- пропускаются бинарные файлы и служебные каталоги;
- ошибки доступа учитываются в результате, а не молча теряются;
- ограничиваются размер отдельного файла и общее число результатов.

Аннотации: `readOnlyHint=true`, `destructiveHint=false`.

### 5.5. `exec_command`

Вход:

```json
{
  "command": "go test ./...",
  "cwd": "C:\\projects\\app",
  "timeout_seconds": 1200,
  "yield_time_ms": 10000
}
```

- `command` и `cwd` обязательны;
- Windows использует PowerShell без профиля, Unix — `/bin/sh` или доступный
  системный shell;
- stdout и stderr с первой секунды пишутся в файл журнала;
- если процесс завершился до `yield_time_ms`, инструмент сразу возвращает код
  выхода, длительность и ограниченный хвост вывода;
- если процесс продолжает работу, инструмент возвращает `status=running`,
  `session_id` и путь журнала;
- весь вывод никогда не накапливается в RAM;
- максимальный размер журнала ограничен конфигурацией;
- истечение `timeout_seconds` завершает всё дерево процессов и сохраняет уже
  записанный журнал.

Аннотации: `readOnlyHint=false`, `destructiveHint=true`, `openWorldHint=true`,
потому что произвольная команда может менять файлы и обращаться к сети.

### 5.6. `poll_command`

Вход:

```json
{
  "session_id": "proc_...",
  "offset": 0,
  "max_bytes": 65536
}
```

Возвращает:

- `running`, `exited`, `failed`, `timed_out` или `cancelled`;
- код выхода после завершения;
- новые байты журнала и следующий `offset`;
- длительность и путь журнала.

### 5.7. `cancel_command`

Вход:

```json
{
  "session_id": "proc_..."
}
```

Завершает всё дерево процессов. Повторная отмена уже завершённой команды должна
быть безопасной и возвращать её конечный статус.

## 6. MCP-visible данные

Во всех ответах, доступных подключённому ИИ:

- `serverInfo.name`: `local-workspace`;
- `serverInfo.title`: `Local Workspace`;
- отсутствуют названия моделей, reasoning/thinking и диалоговые сессии;
- нет инструментов с универсальным полем `prompt`;
- нет MCP resources и UI-карточек;
- `tools/list` содержит ровно перечисленные инструменты;
- описания говорят только о фактической локальной операции;
- каждый инструмент имеет `inputSchema`, `outputSchema` и корректные
  `annotations`.

Добавить автоматический тест, который сериализует `initialize`, `tools/list` и
типовые результаты, приводит их к нижнему регистру и проверяет отсутствие
запрещённых терминов.

## 7. Рабочие каталоги и доступ к файлам

Глобальный `lastCwd` удалить. Каждый вызов обязан быть самодостаточным:

- файловые инструменты получают явный абсолютный `path`;
- команда получает явный абсолютный `cwd`;
- параллельные вызовы не влияют друг на друга;
- относительный путь разрешается только относительно `cwd`, переданного в том
  же запросе;
- путь очищается через `filepath.Clean` и проверяется до операции.

Добавить настройку:

```text
WEBCODEX_ALLOWED_ROOTS=C:\projects;D:\work
```

Значение `*` сознательно разрешает весь диск. По умолчанию разрешена только
директория запуска агента. Проверять необходимо также итоговый путь после
разрешения symlink/reparse point, насколько это позволяет ОС.

Важно: разрешённый `exec_command` по определению может обойти файловые
ограничения. Поэтому право на shell управляется отдельно через существующие
`AllowedTools`/`DeniedTools` и явно показывается в админке.

## 8. Долгие процессы и журналы

### 8.1. Хранилище процесса

Внутри локального агента хранить минимальную map:

```text
session_id -> command, process, status, started_at, finished_at, exit_code, log_path
```

Доступ защищается mutex. Отдельную БД для процессов не добавлять.

### 8.2. Журналы

- каталог задаётся `WEBCODEX_LOG_DIR`;
- значение по умолчанию: `logs` рядом с бинарником агента;
- имя: `<UTC timestamp>-<session_id>.log`;
- запись идёт потоково;
- успешный и ошибочный запуск всегда оставляет журнал;
- в ответ возвращается хвост, а не весь файл;
- старые журналы и завершённые process-сессии удаляются по TTL;
- значения по умолчанию: TTL 24 часа, максимум 50 МБ на журнал;
- параметры допускают настройку через environment без создания отдельной
  конфигурационной системы.

### 8.3. Завершение дерева процессов

- Windows: завершать дерево, а не только родительский PowerShell;
- Unix: запускать процесс в отдельной process group и завершать группу;
- после отмены дождаться завершения и закрыть журнал;
- при остановке агента корректно отменить активные процессы либо оставить их
  только при явно выбранной политике. В первой версии — отменять.

Интерактивный stdin и PTY не добавлять до появления реальной задачи, которая
не решается обычной неинтерактивной командой.

## 9. Надёжность Gate ↔ Agent

### 9.1. Устаревшие запросы

Добавить в `protocol.AgentRequest` абсолютный deadline. Агент проверяет его до
начала операции. Просроченный запрос возвращает ошибку и ничего не выполняет.

При замене stream старый поток отменяется, а запросы с истёкшим deadline не
переезжают на новое подключение.

### 9.2. Таймауты

Файловые операции и запуск команды должны возвращаться быстро. Долгую работу
продолжает process session, поэтому Gate больше не обязан держать HTTP-вызов 20
минут.

Рекомендуемые значения:

- Gate tool call timeout: 60 секунд;
- `exec_command.yield_time_ms`: максимум 30 секунд;
- реальный срок команды задаёт `timeout_seconds` и контролирует локальный агент;
- результат после серверного таймаута не теряется, потому что остаётся в
  process session и журнале.

### 9.3. Ограничения входа и выхода

- ограничить размер HTTP body на `/mcp` и `/agent/result`;
- ограничить размер одного JSON-RPC сообщения в NDJSON scanner;
- ограничить объём текста в MCP-ответе;
- не обрезать UTF-8 посередине символа;
- возвращать признак `truncated` и путь/offset для продолжения чтения.

## 10. Безопасность

Функциональность shell намеренно опасна, поэтому безопасность не должна быть
скрыта за названием режима.

Обязательные меры:

1. Сохранять токены только в виде SHA-256 хеша, как сейчас.
2. Не писать токены и OAuth secret в журналы.
3. Проверять `AllowedTools`/`DeniedTools` до отправки вызова агенту.
4. Ограничить OAuth redirect URI известными callback-адресами ChatGPT.
5. Разрешить только PKCE `S256`; убрать `plain` и необязательный challenge.
6. Ограничить размеры request body.
7. Добавить простое ограничение частоты на OAuth token/authorize и MCP ошибки
   авторизации либо обеспечить его на reverse proxy.
8. Уменьшить срок access token или документировать обязательную ротацию.
9. Явно показывать в админке, что `exec_command` даёт удалённое выполнение
   команд с правами пользователя локального агента.
10. Запускать агент не из-под администратора, если конкретная задача этого не
    требует.

## 12. Тестирование

### 12.1. Unit-тесты executor

- `tools/list` содержит ровно семь инструментов;
- неизвестный инструмент не создаёт файлов и не запускает команд;
- чтение целого файла и диапазона строк;
- чтение пустого файла;
- атомарная запись и запись пустой строки;
- Unicode в путях и содержимом;
- листинг пустого и заполненного каталога;
- поиск, лимит результатов и пропуск бинарных файлов;
- команда с exit code 0;
- команда с ненулевым exit code;
- timeout сохраняет частичный журнал;
- долгая команда возвращает session ID;
- poll возвращает только новые данные от offset;
- cancel завершает дерево процессов;
- параллельные cwd не смешиваются;
- выход за allowed roots отклоняется.

### 12.2. Сквозной тест

Один тест обязан поднять настоящий `httptest` Gate и настоящий локальный agent
loop, после чего пройти путь:

1. OAuth access token или заранее созданный тестовый token.
2. Подключение `/agent/stream`.
3. MCP `initialize`.
4. MCP `tools/list`.
5. `write_file` во временную директорию.
6. `read_file` и сравнение байт.
7. `exec_command`, печатающий строку `TEST`.
8. Проверка stdout и exit code.
9. Долгая команда, `poll_command`, завершение и проверка журнала.

Фейковый echo-agent в этом тесте не использовать.

### 12.3. Отказы и безопасность

- запрос без Bearer token получает 401;
- token одного агента не завершает запрос другого;
- запрещённый `exec_command` не доходит до локального компьютера;
- повторное использование OAuth code отклоняется;
- неверный redirect URI отклоняется;
- PKCE без S256 отклоняется;
- просроченный queued request не исполняется после reconnect;
- слишком большой body отклоняется 413;
- результат не содержит секретов.

### 12.4. Обязательные команды проверки

```powershell
go test -count=1 ./...
go vet ./...
go build -o webcodex-agent.exe ./cmd/agent
go build -o bin/webcodex-gate.exe ./cmd/gate
```

Race detector запускать в CI/Linux или Windows-среде с рабочим CGO.

Все длительные проверки должны писать stdout/stderr в отдельный лог, чтобы
результат не пропадал при таймауте терминала.

## 13. Порядок реализации

### Этап 1. Зафиксировать новый контракт

- добавить тест ожидаемого `tools/list`;
- добавить тест отсутствия запрещённых терминов;
- добавить тест неизвестного старого инструмента без побочных действий;
- пока не менять Gate и deployment.

Критерий: новые тесты падают на текущей реализации по ожидаемой причине.

### Этап 2. Переписать файловый executor

- удалить regex и универсальные инструменты;
- реализовать read/write/list/search;
- удалить `lastCwd`;
- добавить allowed roots и лимиты;
- заменить старые тесты минимальными контрактными тестами.

Критерий: файловые unit-тесты проходят, количество кода уменьшается.

### Этап 3. Реализовать процессы и журналы

- реализовать exec/poll/cancel;
- потоково писать лог;
- ограничить RAM и размер журнала;
- реализовать timeout и завершение дерева;
- добавить TTL cleanup.

Критерий: команда, работающая дольше HTTP-вызова, завершается и её полный
результат доступен через журнал и polling.

### Этап 4. Упростить Gate и протокол

- нейтрализовать MCP-visible metadata;
- убрать tool cards/resources;
- добавить request deadline и body limits;
- выровнять таймауты;
- усилить OAuth redirect/PKCE.

Критерий: Gate не содержит специальной логики второго ИИ и не рекламирует её.

### Этап 5. Добавить настоящий E2E

- соединить реальный Gate и executor в тесте;
- проверить файл, команду, долгий процесс, reconnect и policy deny;
- сохранить логи тестов.

Критерий: тест ломается при подмене результата листингом или при отсутствии
реальной записи на диск.

### Этап 6. Удалить мёртвый код

- удалить старый MCP proxy;
- удалить `third_party/codex`;
- удалить устаревшие тесты и документацию;
- проверить `rg` по запрещённым именам в MCP-visible коде;
- выполнить полную сборку.

Критерий: проект собирается без vendored-движка и без внешнего локального ИИ.

## 14. Развёртывание

1. Сделать резервную копию SQLite и текущих бинарников.
2. Собрать новые Gate и agent с номером версии/commit SHA.
3. Развернуть Gate и проверить `/healthz` и OAuth metadata.
4. Остановить старый локальный агент.
5. Заменить бинарник и запустить новый агент с тем же agent token.
6. Проверить ONLINE в админке.
7. Проверить MCP `initialize` и `tools/list` через Inspector.
8. Для сброса кеша схемы добавить новый endpoint `/mcp/v3` или полностью
   переподключить MCP connector.
9. Начать новый чат и проверить все семь инструментов.
10. Только после успешной проверки удалить старые бинарники.

Нельзя считать обновление завершённым, если старый разговор продолжает видеть
закешированный список инструментов.

## 15. Откат

- Gate и agent разворачиваются отдельными версионированными бинарниками;
- SQLite schema на первой переделке не менять;
- при ошибке остановить новый агент, вернуть предыдущий бинарник и перезапустить;
- Gate откатывать только если сломан OAuth или routing;
- журналы команд сохранить для диагностики;
- не возвращать regex-fallback как временное решение.

## 16. Критерии готовности

Работа считается завершённой только если одновременно выполнены все условия:

- `tools/list` содержит только семь локальных инструментов;
- в MCP-visible JSON нет запрещённых названий, моделей и thinking;
- запрос записи создаёт файл строго по переданному пути и с точным содержимым;
- произвольный текст не интерпретируется агентом как команда или имя файла;
- короткая команда возвращает реальный stdout, stderr и exit code;
- долгая команда возвращает session ID и непрерывно пишет журнал;
- timeout и cancel завершают дерево процессов;
- параллельные запросы не смешивают cwd;
- просроченный запрос не выполняется после reconnect;
- политика Gate может полностью запретить shell конкретному агенту;
- сквозной тест использует настоящий Gate и настоящий executor;
- `go test`, `go vet` и обе сборки проходят;
- новый connector проверен в новом чате после сброса кеша инструментов.

## 17. Предлагаемая разбивка коммитов

1. `test(agent): lock down local MCP tool contract`
2. `refactor(agent): replace prompt parser with explicit file tools`
3. `feat(agent): add logged command sessions`
4. `fix(gate): add deadlines limits and neutral MCP metadata`
5. `test(e2e): exercise real gate and local executor`
6. `chore: remove unused engine and legacy tool UI`
7. `docs: update local MCP deployment and recovery guide`

Каждый коммит должен собираться и проходить относящиеся к нему тесты. Не
смешивать функциональную переделку с форматированием посторонних файлов.
