# Следующий этап: быстрый, спокойный и отказоустойчивый браузерный агент

Дата: 2026-10-24, Asia/Qyzylorda. Проанализирована ревизия `7c1fd15` после первой
серии исправлений. План выполняется: поставка A и пункт B1 завершены; оставшиеся
B/C/D/E ещё предстоит реализовать. Результаты проверок приведены в разделе 14.
Рабочий браузер и сайты не использовались.

Учтены обе задачи пользователя: ускорить и облегчить работу агента, повысить
стабильность; по возможности сделать управление менее заметным и похожим на
обычную работу человека.

## 1. Главный вывод

Наибольший эффект дадут четыре изменения: запрет просроченных действий на каждом
этапе, очереди с приоритетной отменой, сокращение повторных внутренних запросов,
сохранение работоспособности агента при сбое браузерной подсистемы. Затем —
бережное управление фокусом и ввод через обычные механизмы браузера.

Повышение надёжности должно уменьшать число повторов и служебных действий.
Случайные долгие паузы, имитация опечаток и постоянные переподключения увеличивают
время и количество состояний, которые приходится восстанавливать. Процентное
ускорение пока не измерено; ниже отдельно указаны наблюдения и целевые критерии.

## 2. Что удалось подтвердить

Три Go-пробы выполнены через временный `go test -overlay` с `net.Pipe` и
изолированными временными каталогами. Ещё две — в Node VM на настоящем коде
service worker с тестовым Chrome API. Исходники runtime не менялись.

| Наблюдение | Доказательство и границы |
| --- | --- |
| Команда уходит в bridge при уже отменённом context | Прямой вызов `callFrame` с отменённым context передал `Input.dispatchMouseEvent` в net.Pipe, затем вернул context.Canceled. Это проверка транспорта, без реального клика |
| Очередь расширения не знает срок всей browser operation | В VM первая команда удерживалась, вторая ждала; после отметки истечения операции и снятия удержания вторая дошла до mock Input. В протоколе команды сейчас нет такого deadline/cancel/epoch |
| Обычный snapshot имеет лишние обходы | На warm personal frame без дочерних targets полный `tabAction(browser_snapshot)` сделал 10 вызовов: 4 Page.getFrameTree, 4 WebCodex.frames, Runtime.evaluate и AX. Это счётчик mock IPC, не замер задержки реального сайта |
| Повреждение одного journal record мешает всему агенту | Одна некорректная bop-запись привела к отказу `newNativeExecutorWithConfig` при initialize browser. Проверено на отдельном временном каталоге |
| Символы считаются вместо байтов | `post({text:'я'.repeat(600000)})` прошёл проверку длины в SW; JSON занимает 1 200 011 байт UTF-8 и превышает локальный bridge limit 1 MiB |

Важно различать окончание HTTP/MCP-ожидания и срок browser operation. Потеря
ответа клиенту сама по себе не должна останавливать уже начатую операцию:
её результат восстанавливается по request_key. Для явной отмены операции,
локальной паузы и истечения её собственного срока нужны отдельные гарантии.

Дополнительные выводы по исходникам, без воспроизведения под нагрузкой:

- `s.mu` удерживается на всё действие, включая wait до 25 секунд; другие вкладки
  той же сессии и чтение diagnostics могут ждать вместе с ним.
- Одна Promise-цепочка `serial` обслуживает команды всех вкладок подключения.
  У неё нет явного ограничения длины, срока ожидания или отмены отдельной записи.
- В `serveBridge` обработка url_check синхронно вызывает checkURL, включая DNS.
  Пока она занята, общий reader не разбирает ответы и события этого соединения.
- При каждом wait tick eval снова перечисляет frames. В scoped snapshot сначала
  выполняется walk(document), затем обход выбранного контейнера.
- Операции пишут journal и делают Sync под общим `b.mu`. Вытеснение операций
  также просматривает/сортирует общий кеш под этим mutex.
- При смене кода ошибки на outcome_unknown не везде пересобирается recovery.
  Код, стадия исполнения и инструкция восстановления должны формироваться вместе.
- Managed iframe contexts накапливаются в map с лимитом 64; явного удаления
  уничтоженных targets и хранения их cancel handles в этом пути нет.
- При клике безусловно вызывается Page.bringToFront, а elementPoint всегда
  прокручивает элемент к центру. Это может мешать человеку и двигать страницу.

## 3. P0: запрет запоздалых действий и однозначная отмена

Код: `browser.go: call/execute/control`, `browser_bridge.go: callFrame`,
`browser-extension/background.js: onMessage/serial/execute`.

Предлагаемый контракт команды: operation_id, command_id, connection_epoch,
scope_epoch, deadline операции и номер шага. Эти поля задаёт доверенный agent;
модель не передаёт произвольный JavaScript или привилегии. Время ожидания
в очереди входит в срок операции.

Проверки нужны до помещения в очередь, после ожидания блокировки, перед IPC send,
при извлечении из очереди SW и непосредственно перед изменяющим вызовом CDP.
После reconnect или смены локального доступа старые epochs недействительны.
На одном компьютере можно сопоставлять wall-clock deadline с ограниченным
remaining budget и локальным монотонным временем; изменение часов не должно
продлевать уже истёкшую задачу.

Отмена получает отдельный приоритетный путь. Go удаляет ожидающую команду,
SW подтверждает снятие записи, локальные observers/timers освобождаются.
Ожидание отмены тоже ограничено. Закрытие старого порта не означает разрешение
повторить команды на новом соединении.

Состояния операции:

```text
reserved → queued → dispatch_started → dispatch_ack → observing → verified
                ↘ cancelled_before_dispatch
                         ↘ outcome_unknown, если эффект нельзя установить
```

Резервирование должно завершиться до отправки мутации. Уже отправленный click
нельзя обещать отменить задним числом. Если неизвестно, применён ли он,
необходима проверка сайта перед новым действием. Нужен единый finalizer для
code/message/recovery/phase вместо независимого изменения этих полей.

Приёмка: отменённая queued mutation не достигает mock dispatch; локальная пауза
с последующим resume не оживляет старую очередь; поздний response не меняет
новую операцию; повтор request_key не создаёт вторую отправку. Отдельно проверить
cancel между mouseDown/mouseUp и неоднозначный исход уже отправленного действия.

MCP cancellation может запаздывать и не отменять завершённую работу; протокол
требует корректно обрабатывать такие гонки. Это не заменяет отмену бизнес-операции
внутри browser_control. [Спецификация MCP](https://modelcontextprotocol.io/specification/2025-06-18/basic/utilities/cancellation).

## 4. P0/P1: очереди и изоляция медленных действий

Ввести явный ограниченный scheduler. Сначала сохранить одного изменяющего
исполнителя на профиль; это защищает общие cookies/auth и связанные формы.
Сериализовать последовательность действий одной вкладки. Распараллеливание
записи в нескольких вкладках добавлять только после тестов конфликтов аккаунта.

Приоритеты: локальная пауза/отзыв/отмена → короткие health/status/diagnostics →
UI-действия → объёмные чтения и screenshots. Status и накопленная диагностика
должны читаться без ожидания session mutex и исправности DOM/renderer.

Длительное ожидание хранит условие и ownership вкладки, но не удерживает общий
mutex профиля. Настоящее чтение страницы в той же вкладке остаётся согласованным
с её состоянием; параллельный snapshot не должен незаметно уничтожать IDs
выполняющейся операции. Чтение накопленных метаданных не требует нового snapshot.

Начальные queue limits определить небольшими и настраиваемыми, например до
8 ожидающих действий на профиль; это кандидат настройки, не измеренный оптимум.
При переполнении возвращать busy/retry_after до принятия новой мутации.
Число goroutines, bytes и время ожидания ограничивать отдельно от числа записей.

Приёмка: wait одной вкладки не блокирует status и диагностику другой; очередь
не растёт бесконечно; каждая просроченная запись удаляется до dispatch. Graceful
shutdown прекращает приём, отменяет очередь, фиксирует исходы и ограниченно
дожидается writer/active operations без закрытия личного браузера пользователя.

## 5. P1: сеть не должна задерживать весь IPC reader

Оставить reader быстрым: разбор message → маршрутизация → продолжение чтения.
Проверки URL передать ограниченному пулу, а policy replies — приоритетному writer.
Запрос одного медленного DNS не должен задерживать cancel, response и другие host.

Добавить объединение одинаковых одновременных проверок host, небольшой bounded
cache с коротким TTL и привязкой к версии политики. Кешировать hostname→проверенный
результат можно только с сохранением проверок IP/redirect/private networks;
долгое кеширование allow по имени создаёт риск устаревшего решения. Отзыв доступа
немедленно инвалидирует соответствующие решения. При неизвестном результате
запрос не разрешается автоматически.

Время обработки paused request измерять отдельно. Fetch действительно держит
запрос до ответа обработчика, поэтому задержка проверки влияет на загрузку сайта.
[Описание Fetch.enable/requestPaused](https://chromedevtools.github.io/devtools-protocol/tot/Fetch/).

Scope updates объединять по принципу «последнее состояние», сокращая повторные
tabs.query и отправки одинаковых каталогов. Пауза и отзыв доступа применяются
немедленно, независимо от debounce обычных title/active updates. Сохранять
request terminal events; диагностические повторы можно агрегировать со счётчиком.

Приёмка: искусственно медленный DNS не блокирует IPC responses; все проверки
redirect и scope продолжают проходить; нет накопленных paused requests после
разрыва, отмены и локальной паузы.

## 6. P1: меньше запросов, меньше DOM-работы и данных для модели

### Состояние frames на время операции

Сначала передавать уже разрешённый frame context внутри одной операции из
tabAction в snapshot/eval, убрав повторные одинаковые перечисления. Затем —
кеш live frames, isolated worlds и OOPIF sessions с событийной инвалидизацией.
Неизвестный frame или gap/reconnect требует reconcile. Уничтоженные contexts
удаляются вместе с cancel handles и observers.

Кеш не заменяет разрешения: перед чтением/действием renderer должен подтвердить
ожидаемые URL/document generation и policy epoch. При расхождении возвращается
frame_changed, данные нового документа не собираются под старым разрешением.

Цель стенда для warm light snapshot без iframe: сократить базовые 10 внутренних
вызовов до ≤3. Full AX и восстановление topology измеряются отдельно.

### Чтение нужной области

- Scoped snapshot начинает обход непосредственно с контейнера.
- Точный CSS locator использует точный запрос; полный walk нужен только для
  семантического поиска/open shadow roots и имеет явный budget.
- Light snapshot возвращает нужные элементы и короткий текст; полное AX —
  опционально. Повторение одного текста в body/AX/labels уменьшать.
- Установленные доверенные helper functions можно переиспользовать в isolated
  world с версией, передавая аргументы. Их нельзя превращать в API произвольного JS.
- После собственного действия возвращать короткий результат: changed/selected,
  стадия, условия проверки. Большой новый snapshot нужен при смене состояния,
  неожиданной ошибке или запросе чтения.
- При необходимости ограниченный ring snapshots по frame/generation позволяет
  безопасно читать соседнюю секцию. Нужны TTL, byte budget, node liveness checks;
  недействительные IDs не переназначаются новому элементу с тем же номером.

Структурированный и текстовый MCP-ответ сейчас дублируются для совместимости.
Сокращать их до одного представления можно только для проверенного клиента;
сначала достаточно уменьшить сам snapshot и число повторных чтений.

### Ожидание рядом со страницей

Заменить частый транспортный polling на доверенный локальный wait: один observer
на нужную область, конкретное условие, timeout и cancel cleanup. Для layout —
проверка геометрии и hit-test целевого элемента. Оставить bounded polling fallback.
Не ждать полной тишины сети/всего DOM: аналитика и анимации могут работать постоянно.

Приёмка: delayed suggestions/hydration, iframe replacement, shadow roots,
крупный DOM и непрерывная анимация. Считать IPC calls, JS bytes и время layout,
а не только итоговую задержку. Целевое ускорение в процентах установить после baseline.

## 7. P1: отказ браузера не должен останавливать файловый агент

Ввести явный health браузерного provider и режим ограниченной работы. Повреждённая
запись, недоступный Chrome или неисправное расширение не должны мешать запуску
read_file, обычных команд и остальных независимых инструментов.

Повреждённый journal нельзя просто пропустить: это может убрать защиту от
повторной мутации. Изолировать файл, сохранить evidence/индекс ключа и закрыть
запись для затронутого ключа. Если ключ/индекс восстановить невозможно, браузерные
мутации остаются заблокированными до восстановления; остальные инструменты и
доступные безопасные чтения продолжают работать с понятным health reason.

Вынести durable writes из общего b.mu в ограниченный writer. Под mutex только
резервируется состояние; исполнитель получает разрешение dispatch после
подтверждённой записи резерва. При disk-full запись не выполняется, pending
requests завершаются предсказуемо. Кеш ограничить байтами и числом записей,
добавить уборку закрытых sessions/frames/artifacts.

Сначала сохранить текущий формат atomic files с индексом и версиями записей.
При больших измеренных объёмах сравнить его с transactional store. SQLite уже
есть в модуле Gate, но импорт в agent имеет отдельную цену по размеру/памяти;
миграцию выбирать по нагрузке, восстановлению и стоимости сопровождения.

TTL request keys задокументировать как ограничение гарантии: после удаления ключа
нынешний сервер не знает о старом запуске. Для опасных действий рассмотреть
долгоживущие компактные tombstones/выданные сервером intent IDs с явным expired
ответом. Изменение semantics старых v5 ключей требует отдельного совместимого
решения. Общая гарантия остаётся: неизвестный эффект сайта не повторяется вслепую.

## 8. P1/P2: байты и изображения ограничивать до передачи

В SW считать UTF-8 bytes (`TextEncoder`), а не длину JS string. Согласовать
единый envelope budget на SW → native host → agent → Gate → MCP. Проверять
кириллицу, emoji и escaping, оставлять место для служебных полей.

Chrome документирует разные пределы направлений Native Messaging: 1 MB от host
в extension и 64 MiB в обратную сторону. В проекте действует дополнительный
локальный 1 MiB cap, который тоже нужно соблюдать.
[Native Messaging protocol](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging).

Большой personal screenshot сейчас может не пройти transport ещё до Go resize.
Поэтому подобрать capture scale/quality до отправки, оставить небольшой preview
и отдельный full artifact по запросу. Если понадобятся chunks — ограничить окно,
общий размер, сроки, порядок и integrity; незавершённые сборки удалять. Это второй
шаг после правильного byte budget, не обязательное усложнение первой поставки.

В Go декодировать оригинал один раз, оценивать base64 размер по длине без
повторной EncodeToString и ограничить число попыток resize. Область интереса
часто полезнее сильно уменьшенного полного экрана. Критерий качества — читаемость
текста и доступность реального payload/artifact при соблюдении бюджета.

## 9. P2: короткие сценарии, checkpoints и восстановление

Добавить ограниченные декларативные операции: заполнить несколько полей,
выбрать option, дождаться результата, проверить сохранение. Общие preflight,
ownership вкладки и журнал шагов позволяют сократить диалог с моделью. Это
должны быть типизированные действия поверх существующего разрешённого API.

Batch не является транзакцией сайта: уже заполненное поле может запустить
autosave. При частичном выполнении возвращать номера завершённых шагов и
неопределённых эффектов. Checkpoint содержит безопасные IDs, желаемое состояние,
границы подтверждения и ссылку на разрешённый черновик. Пароли и auth storage
в checkpoints не входят. После рестарта сначала reconcile видимого состояния.

Отдельно предусмотреть восстановление потерянного результата Gate без повторного
браузерного действия: bounded retry доставки того же ответа, operation status
и список последних безопасных operation metadata. Для read-only результатов
можно повторить чтение после проверки контекста; мутации не перезапускаются.

## 10. P2: health, совместимость и понятное восстановление

Handshake: agent build revision, extension version, поддерживаемые capabilities,
версии envelope/helper scripts. После reconnect новые connection epoch и IDs;
неподдерживаемое действие отклоняется до изменения страницы.

Heartbeat нужен для обнаружения зависшего соединения с таймаутом, backoff и
jitter; работа локальной паузы не должна порождать бесконечный auto reconnect.
Не создавать heartbeat только для удержания worker живым: Chrome уже учитывает
connectNative и активный debugger при его lifecycle, но termination всё равно
нужно обрабатывать. [Chrome service worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle).

Различать provider_unavailable, page_unresponsive, renderer_gone, user_detached,
policy_paused и recoverable context loss. Circuit breaker — для конкретного
provider/tab/origin, с ограниченным чтением-пробой после паузы. Ошибка preview
одного сайта не должна блокировать весь Chrome; permission errors не лечатся
повторами. Сохранять первопричину/стадию вместе с безопасной категорией.

## 11. Как сделать работу менее заметной и более естественной

### Фокус и отдельное рабочее окно

Предлагаемые настройки: `focus_policy=preserve|if_needed|always` и отдельное
закреплённое окно/группа вкладок агента. В personal это может быть другое окно
того же профиля с разрешёнными вкладками; cookies никуда не копируются.

При preserve чтение и совместимые действия идут без Page.bringToFront.
Если сайт действительно требует переднего плана, возвращается attention_required
с понятной причиной. Silent fallback с захватом фокуса не нужен. Текущий режим
совместимости сохраняется до отдельной проверки фоновых сценариев Chrome/Edge.

Владение фокусом и выбранная вкладка проверяются перед вводом: агент не печатает
в поле, в которое человек только что перешёл. Надёжная локальная pause/shortcut
должна останавливать очередь. Дополнительная автопауза при активности человека
сохраняет только признак/время активности; один isTrusted не позволяет надёжно
разделить пользовательский и браузерный ввод агента. Обнаружение может быть
best-effort, а явная локальная пауза должна работать детерминированно.

### Действия, которые выглядят обычными

- Не прокручивать страницу, если элемент уже доступен. При необходимости —
  минимальное смещение вместо постоянного центрирования каждого поля.
- Использовать браузерный pointer/keyboard/text input для форм, где важен
  обычный input pipeline. Рассмотреть Input.insertText для Unicode/вставки и
  корректный focus/selection/input/change; сохранить проверенный fallback.
  [Методы Input в используемом проекте CDP](https://github.com/chromedp/cdproto/blob/main/input/input.go).
- Длинный About обычно удобнее вставить целиком, чем искусственно печатать
  тысячи символов. Для полей с обработкой клавиш нужен отдельный режим ввода.
- Ожидать готовность интерфейса и соблюдать заданный темп сценария; не добавлять
  имитацию ошибок и движений, которые не помогают выполнить задачу.
- Никаких отладочных рамок/лейблов в DOM сайта. Статус и журналы — в popup/агенте.
  Системный курсор и чужие вкладки не используются как рабочая область.
- При CAPTCHA, авторизации и подтверждениях передавать управление человеку,
  затем продолжать с нового подтверждённого состояния.

Сейчас часть fill/select идёт через native setters и синтетические DOM events.
Замена на другой input path требует тестов редакторов, IME/кириллицы, undo и
autosave; автоматически менять все поля сразу было бы рискованно. Проверять
последовательность событий, сохранённый текст и отсутствие потери фокуса.

### Что заметит сайт и что можно обещать

Снижение лишних действий и обычный ввод не дают гарантии, что сайт всегда
примет автоматизацию за человека. WebDriver имеет стандартный automation
indicator; наш CDP transport не равен WebDriver, и значение отдельного флага
не доказывает ни наличие человека, ни отсутствие автоматизации.
[W3C WebDriver interface](https://w3c.github.io/webdriver/#interface).

Уведомления самого Chrome и ограничения debugger принадлежат браузеру;
у расширения нет универсальной гарантии скрыть их для всех версий/политик.
API chrome.debugger предусматривает в том числе пользовательское отключение.
[Chrome debugger API](https://developer.chrome.com/docs/extensions/reference/api/debugger).

Практические критерии: нет неожиданных переключений вкладок/фокуса, нет лишних
прыжков страницы, корректный ввод и сохранение, локальная остановка доступна.
Невидимость автоматизации для всех сайтов нельзя использовать как обещание
готовности продукта. Пользователь должен видеть состояние своего агента.

## 12. Как измерять результат

Нужен воспроизводимый локальный стенд с сопоставимыми браузерами и страницами:
простая форма, большой DOM, iframe/OOPIF/shadow, редактор, delayed autocomplete,
preview failure, длинная форма. Отдельно — реальное расширение в тестовом профиле,
поскольку Node VM и IPC adapter не проверяют весь lifecycle Chrome.

Метрики: p50/p95 по стадиям queue/policy/CDP/verification/persistence, IPC calls,
bytes/snapshot, allocations/RSS, active observers/frames, journal size/startup,
focus changes и число подтверждённых/неизвестных/повторённых effects. Диагностика
собирает длительности и категории, без текстов полей и секретов.

Обязательные fault cases: отмена на каждой стадии; истёкшая запись в очереди;
пауза→resume; смерть renderer/SW/host; оборванный port; поздний response; медленный
DNS; заполненный диск; повреждённая запись; утрата operation result; смена аккаунта
или документа; overflow/chunk truncation; пользовательский ввод во время работы.

Критерии первой поставки следующего этапа:

1. Ни одной отправки mutation после подтверждённой отмены до dispatch.
2. Status/накопленные diagnostics не ждут чужого длительного wait.
3. Warm light snapshot ≤3 внутренних вызовов на простом personal frame;
   scope и navigation проверки сохраняются.
4. Повреждение browser journal не мешает независимым инструментам; неопределённая
   мутация остаётся заблокированной, даже если record quarantined.
5. UTF-8 payload не превышает заявленный byte budget.
6. В focus_policy=preserve нет непрошеного вывода окна на передний план.
7. Crash/reconnect/повтор result delivery не создают второго submit.

Latency/RAM цели зафиксировать по baseline. Нулевые дубли в fault-тестах —
проверяемое требование; это не обещание exactly-once для произвольного сайта.

## 13. Порядок реализации

| Поставка | Состав | Почему в этом порядке |
| --- | --- | --- |
| A | deadline/cancel/epoch, стадии, единый outcome finalizer, ограниченная очередь, fault tests | Убирает запоздалые действия; основа спокойной фоновой работы |
| B | быстрый reader/policy path, устранение повторных frame calls, scoped DOM, локальные waits, UTF-8 byte budget | Сокращает ожидания и обмен без потери проверок |
| C | degraded startup, journal writer вне общего mutex, байтовые лимиты кешей, cleanup/drain | Локализует отказы и удерживает ресурсы при длительной работе |
| D | focus policy, закреплённое окно, native input modes, минимальная прокрутка | Делает работу менее заметной после исправления отмены и ownership |
| E | typed batches/checkpoints, result recovery, capabilities и расширенные health tests | Уменьшает число действий модели и упрощает восстановление длинных задач |

Каждая поставка делится на небольшие проверяемые коммиты с немедленным push.
Сначала baseline и отрицательные тесты, затем реализация и сравнение метрик.
Полная смена CDP-движка, новый фоновый daemon и миграция всего журнала в БД
не являются предварительными условиями этих улучшений.

## 14. Выполнение и экономное делегирование

Реализация начата 2026-10-24. Каждая строка ниже — отдельный ограниченный этап;
выполненным он становится после проверки diff, тестов, коммита и push родителем.

| Этап | Ответственный и область | Проверка результата |
| --- | --- | --- |
| Подготовка | Основной агент: этот документ, границы задач и протокола | Независимые file ownership, список инвариантов |
| B1: UTF-8 byte budget | Leaf: только post и его Node tests в background.js/background.test.cjs | ASCII/Cyrillic/emoji и граница 900000 байт |
| A1: единый error finalizer | Leaf: browser_errors.go и отдельный unit-test файл | outcome_unknown всегда соответствует verify_outcome, контекст не теряется |
| A2: сроки и отмена IPC | Основной агент: browser_bridge.go, browser.go и транспортные тесты | Уже отменённый context ничего не отправляет; поздняя команда не исполняется |
| A3: очередь расширения | Основной агент после B1: deadline/epoch/cancel и bounded queue | Просроченная/отменённая запись удаляется до dispatch; pause/resume не оживляет её |
| A4: интеграция | Основной агент: стадии операции, schema, guide, проверка совместимости | Согласованные code/message/recovery; retry не повторяет mutation |
| B/C/D/E | Следующие волны по зависимостям раздела 13 | Отдельные ограниченные задания после готовности контрактов |

Для leaf-заданий передаются только пути, конкретный результат, инварианты и
команда проверки; полная история диалога не копируется. Используется минимальная
подходящая модель, короткий итог, без самостоятельного расширения задачи.
Основной агент сохраняет архитектуру, разрешения, интеграцию, commit/push.
Не запускать отдельного агента ради тривиального изменения или повторного чтения
того, что уже проверено. Не дублировать реализацию и не поручать двум агентам
одни файлы одновременно. Общие проверки запускать на границе поставки.

Antigravity CLI обнаружен, но два независимых запуска потребовали авторизацию
до выполнения задач. Они остановлены без изменений. Для текущей волны выбран
доступный fallback: встроенные leaf-агенты с узким контекстом и экономичной
моделью. Настройка OAuth не входит в реализацию браузерного плана.

Обязательные инварианты: локальные pause/scope не обходятся; просроченная queued
mutation не исполняется; потеря ответа сохраняет recovery по тому же request_key;
действие с неизвестным исходом не повторяется; секреты не попадают в журнал;
новые transport features проверяются с явно указанной версией расширения.

Журнал завершения:

- Подготовка: отдельный план дополнен схемой делегирования и критериями этапов.
- Дополнение пользователя: обычная консоль показывает браузерные действия,
  вкладку/title/URL, короткую выдержку прочитанного, итог и длительность. Асинхронное
  завершение видно после окончания RPC-ожидания; ошибки не дублируются, Retry
  не маскируется под новое действие. Значения ввода не выводятся.
- B: scoped snapshot обходит только выбранный контейнер и его shadow roots;
  frame catalog переиспользуется внутри операции с URL/epoch guard. Warm full
  snapshot сокращён с 10 до 4 IPC-вызовов, light — до 3; full AX остаётся default.
  Scope publications объединяются в ограниченные active/next batches. Расширение
  помечено 1.3.1. Остальные пункты B ещё выполняются.
- C (часть): ожидание managed cleanup ограничено; зависшее закрытие не удерживает
  агента бесконечно, pending cleanup блокирует новые mutations до завершения.
  Для удаления временного профиля проверяется его расположение внутри profiles.
- C (startup): неисправность браузерного provider не мешает старту файлов/команд.
  Повреждённый journal остаётся evidence, все browser mutations заблокированы до
  восстановления; discover показывает health/reason. Journal record ограничен
  1 MiB и обычными файлами, отсутствующая дата не считается истёкшим ключом.
- C (cache): добавлен byte budget 32 MiB для результатов, изображений и временных
  ошибок; eviction сохраняет retry index и durable mutation records.
- B1 завершён: post проверяет UTF-8 bytes без повторной сериализации; ASCII,
  кириллица, emoji и точная граница бюджета проверены. Родитель просмотрел diff
  и независимо повторил все 20 Node-тестов расширения.
- A1 завершён: единый setFailureCode обновляет code/message/recovery и сохраняет
  контекст. Родитель подключил его к timeout, ошибке записи и восстановлению
  журнала; targeted finalizer/restart/eviction/retry tests прошли.
- A2–A4 реализованы и проверены: protocol 2 передаёт deadline, connection ID и
  scope epoch; отмена доставляется отдельно от очереди. Контекст проверяется
  перед отправкой. Очереди Go/SW ограничены восемью ожидающими записями; pause,
  cancel и смена доступа отменяют старую работу даже при гонке выдачи permit.
  Ошибки различают not_dispatched и неизвестный исход после начала отправки.
- Приёмка A: Chrome — 160 pass, Edge — 10 pass, Node — 31 pass; targeted race,
  go vet, Linux cross-compile и состав ZIP расширения проверены. Расширение 1.3.0
  требует обновления вместе с агентом для mutations. Подробности и ограничения:
  [BROWSER_STAGE_A_ACCEPTANCE.ru.md](BROWSER_STAGE_A_ACCEPTANCE.ru.md).
- Следующие поставки B (кроме готового B1), C, D и E ещё не выполнены. В частности,
  ускорение snapshot, degraded journal startup и focus_policy=preserve остаются
  в плане. Нельзя считать выполненными все критерии раздела 12 по результатам A.

## 15. Уточнения по тестированию 2026-10-25

Новый postmortem работы с Discord повышает приоритеты ниже. Исходный отчёт
не содержит ревизий запущенных компонентов: проверки исходников не заменяют
проверку установленной версии. Данные канала и его выгрузка не включаются в Git.

1. P0: точное подключение к уже открытой вкладке по URL/profile/window с
   reuse_only. При совпадениях внутри профиля — детерминированный выбор с причиной;
   при неизвестном профиле — явная ошибка. Нельзя подменять личный браузер новым
   persistent или возвращать подтверждённый binding без проверки читаемости.
2. P0: структурированное чтение контейнера с cursor/revision, стабильными IDs и
   явным усечением; прокрутка конкретного контейнера с проверкой изменения его
   содержимого. Достигнутый предел DOM/viewport не означает конец истории.
3. P0: исходные байты видимого вложения через разрешённый браузерный контекст,
   atomic .part, размер/формат/SHA-256 и явный статус. Signed URL не попадает в
   логи/JSON; original_verified нельзя выводить только из размеров изображения.
4. P0: message/attachment IDs связывают текст и файлы; manifest/checkpoint
   восстанавливаются по фактическим завершённым sidecars, а не по памяти процесса.
5. P1: проверка Unicode/undo/autosave, работа без ненужной смены фокуса,
   понятный terminal payload и диагностика выбранной вкладки/окна.

Реализовано в исходниках: reuse_only/exact_url/window_id, проверка читаемости и
binding_revision для последующих действий; версия агента/расширения и capabilities
в discover. Расширение 1.4.0 проверяет target до и после CDP. Добавлены native
Unicode fill с read-back/undo и focus_policy=preserve по умолчанию для click/select.
Durable writer ограничен восемью слотами и работает вне общего b.mu. Проверка
реальной установки Jinn и каналов пользователя остаётся отдельной приёмкой.
Структурированная история/оригинальные вложения/checkpoint из пунктов 2–4 ещё
предстоят; старый текстовый snapshot не считается их реализацией.

Следующая часть P0 реализует generic DOM records: связывает текст и все найденные
вложения по ID записи, выдаёт revision-bound cursor и явные пределы. Контейнерная
прокрутка возвращает видимые/новые IDs после ограниченного ожидания. Полнота
удалённой истории не выводится из DOM. save_download теперь проверяет байты,
SHA/MIME/размеры и распознаёт дубли без перезаписи; оригинальность источника не
утверждается. Быстрая накопленная диагностика и ограниченный URL policy pool
устраняют ещё два вида задержек B. Запуск оригинальных вложений и полный
автоматический экспорт удалённого канала остаются отдельной приёмкой.

Локальная часть checkpoint реализована в tools/browser_capture_store.py: приём
уже скачанных файлов, immutable sidecars, возобновление после частичной записи,
автоматическая пересборка manifest/audit/checkpoint, проверка хэшей и явные
ошибки. Она не собирает удалённую историю и не объявляет её полной.

Приёмка инструментов: локальная виртуализированная история, 10 вложений,
несколько одинаковых URL в разных окнах, reconnect/cancel и restart посередине
сохранения. Live-проверка пользовательского источника отмечается отдельно.
Работы по B/C/D/E сохраняются, но порядок определяется этими P0.
